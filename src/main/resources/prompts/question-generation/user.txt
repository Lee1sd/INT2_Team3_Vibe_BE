다음 이력서 내용과 선택 키워드를 바탕으로 기술 면접 질문 4개와 각 질문의 모범답안을 생성하세요.

## 입력

### 선택 키워드
{{keyword}}

### 이력서 텍스트
{{resumeText}}

## 질문 생성 원칙

- 질문은 반드시 선택 키워드와 이력서에 드러난 경험, 기술, 프로젝트 맥락을 함께 반영하세요.
- 이력서에 선택 키워드와 직접 관련된 경험이 없으면, 이력서 내용을 억지로 끌어쓰지 말고 일반적인 CS 지식 관점에서 질문을 만드세요.
- 이 질문은 매번 새로 생성해야 하며, 미리 정해진 질문 목록에서 고르거나 이전에 생성한 질문을 재사용해서는 안 됩니다.
- few-shot 예시의 문장을 그대로 베끼지 말고, 스타일만 참고해서 이번 이력서/키워드에 맞는 새로운 질문을 만드세요.
- 질문은 turn 1, 2, 3, 4 순서로 난이도가 조금씩 깊어지게 구성하세요.
- 각 모범답안은 핵심 원리 2~3개와 대표 예시 1개 수준으로 간결하게 작성하세요. 채점 기준으로
  쓰이지만, 가능한 구현 방법·기술 패턴을 모두 나열한 완벽한 설계 문서가 아니라 "이 정도면
  충분히 이해했다고 볼 수 있는 최소 기준"을 적으세요.
- 질문과 모범답안에는 사용자에게 노출해도 되는 기술 정보만 사용하고, 개인정보를 새로 만들거나 추정하지 마세요.

## Few-shot 예시

### 예시 1
입력 키워드: DB
이력서 단서: "Spring Boot API에서 게시글 목록 조회가 느려져 실행 계획을 확인하고 인덱스를 조정했다."
출력 질문: "게시글 목록 조회가 느려졌을 때 실행 계획에서 어떤 지표를 보고 인덱스 개선 여부를 판단하셨나요?"
출력 모범답안: "핵심 원리: (1) 실행 계획의 type/rows/Extra로 풀스캔·정렬 여부를 확인한다. (2) WHERE/JOIN에 자주 쓰이는 컬럼의 선택도를 기준으로 인덱스 순서를 정한다. 예시: 게시글 목록 조회라면 조회 조건 컬럼을 선두에, 정렬 컬럼을 뒤에 붙이는 식으로 복합 인덱스를 설계한다."

### 예시 2
입력 키워드: 보안
이력서 단서: "Spring Security와 OAuth2로 로그인 흐름을 만들고 refresh token을 hash로 저장했다."
출력 질문: "refresh token을 원문 대신 hash로 저장하면 어떤 공격 시나리오를 줄일 수 있고, 재발급 요청에서는 어떻게 검증해야 하나요?"
출력 모범답안: "핵심 원리: (1) DB가 유출돼도 원문이 바로 쓰이지 못하도록 단방향 hash로 저장한다. (2) 재발급 요청은 받은 token을 같은 방식으로 hash해 저장값과 비교·검증한다. 예시: 로그인 시 발급한 refresh token을 hash해 저장하고, 재발급 요청이 오면 클라이언트가 보낸 token을 다시 hash해 저장값과 일치하는지 확인한다."

## 출력 검증 규칙

- questions 배열 크기는 정확히 4이어야 합니다.
- turn은 정수 1, 2, 3, 4를 각각 한 번씩만 사용해야 합니다.
- questionText와 expectedAnswer는 빈 문자열이면 안 됩니다.
- expectedAnswer는 API 응답 화면에 노출되지 않고 채점 로직 내부에서만 쓰인다는 전제로 작성하세요.
