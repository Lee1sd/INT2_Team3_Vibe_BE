다음 최초 채점 결과에서 가장 보완이 필요한 문항을 기준으로 꼬리질문 1개와 채점용 모범답안을 생성하세요.

## 입력

### 최저점 문항 번호
{{weakestQuestionId}}

### 원래 질문
{{questionText}}

### 사용자 답변
{{userAnswer}}

### 채점 feedback
{{feedback}}

## 꼬리질문 생성 원칙

- 원래 질문과 사용자 답변, feedback을 근거로 답변에서 부족했던 부분을 정확히 겨냥하세요.
- 이미 충분히 답한 내용을 반복해서 묻지 말고, 빠진 개념·판단 근거·트레이드오프·실무 적용 중 하나를 더 깊게 확인하세요.
- 최초 질문 생성과 같은 면접관 톤을 유지하되, 질문은 하나만 생성하세요.
- few-shot 예시의 문장을 그대로 베끼지 말고, 구조와 깊이만 참고하세요.
- 모범답안은 핵심 원리 2~3개와 대표 예시 1개 수준으로 간결하게 작성하세요. 최종 채점 기준으로
  쓰이지만, 가능한 구현 방법·기술 패턴을 모두 나열한 완벽한 설계 문서가 아니라 "이 정도면
  충분히 이해했다고 볼 수 있는 최소 기준"을 적으세요.
- 개인정보를 새로 만들거나 추정하지 마세요.

## Few-shot 예시

### 예시 1
원래 질문: "캐시를 도입하면서 발생할 수 있는 정합성 문제는 어떻게 처리했나요?"
사용자 답변: "캐시는 DB 부하를 줄여주기 때문에 사용했습니다."
feedback: "캐시 도입 이유만 언급했고, DB와 캐시 간 데이터 정합성 문제와 처리 전략이 빠져 있습니다."
출력 꼬리질문: "DB와 캐시의 값이 서로 달라질 수 있는 상황을 하나 들고, 그 상황에서 어떤 무효화 또는 갱신 전략을 적용할지 설명해 주세요."
출력 모범답안: "핵심 원리: (1) 쓰기 시점에 캐시를 무효화하거나 갱신해 stale read를 줄인다. (2) DB를 기준 데이터로 두고 TTL로 불일치 허용 시간을 제한한다. 예시: 게시글 수정 후 해당 캐시 키를 즉시 삭제하고, 다음 조회 때 DB에서 다시 채운다."

### 예시 2
원래 질문: "인덱스를 추가할 때 어떤 기준으로 컬럼 순서를 정하나요?"
사용자 답변: "조회가 빠르게 되도록 인덱스를 겁니다."
feedback: "조회 성능 개선이라는 목적은 맞지만, 선택도·조건절·정렬·쓰기 비용에 대한 판단 근거가 부족합니다."
출력 꼬리질문: "복합 인덱스를 설계할 때 WHERE 조건, 정렬 조건, 컬럼 선택도를 어떤 순서로 고려할지 예시와 함께 설명해 주세요."
출력 모범답안: "핵심 원리: (1) 동등 조건 컬럼을 먼저, 범위 조건 컬럼을 나중에 둔다. (2) 정렬 조건까지 인덱스로 커버되는지 확인한다. 예시: WHERE status='ACTIVE' AND created_at > ? ORDER BY id라면 status를 선두에, created_at·id를 뒤에 두는 순서로 설계한다."

## 출력 형식

아래 JSON 객체만 반환하세요. 마크다운 코드블록, 설명 문장, 주석은 절대 포함하지 마세요.

{
  "followUpQuestion": "꼬리질문 본문",
  "expectedAnswer": "채점에 사용할 모범답안"
}

## 출력 검증 규칙

- followUpQuestion과 expectedAnswer는 빈 문자열이면 안 됩니다.
- followUpQuestion은 하나의 질문만 포함해야 합니다.
- expectedAnswer는 API 응답 화면에 노출되지 않고 최종 채점 내부에서만 쓰인다는 전제로 작성하세요.
