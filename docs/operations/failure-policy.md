# failure-policy.md — 실패 처리 정책

> 근거: `[기획서] 커리어 던전 v5.1.pdf` 7장(백엔드 기술적 도전 과제), 12장(리스크 및
> 대응 방안), 17장(보안 설계: 파일 보안). 관련 요구사항: NFR-01~NFR-05, NFR-14. 이
> 문서는 `docs/ai/SHARED.md` §3 역방향 추적 ⑤(LLM 응답 방어)의 판단 기준입니다.

## 1. 파일 업로드/파싱 실패 (① 파일 파이프라인)

| 실패 상황 | 처리 |
| --- | --- |
| 허용되지 않은 확장자 | `400` 응답 (NFR-01) |
| 용량 초과(10MB 초과) | `400` 응답 (NFR-01) |
| PDF 매직넘버·PDFBox 검증 또는 TXT/MD UTF-8·평문 검증 실패 | `Resume.parseStatus = FAILED` 저장 후 재업로드 안내 (FR-01) — 자동 재시도 없음 |
| 원본 삭제 단계 | 검증된 동일 ETag 객체 다운로드 후에는 파싱 성공/실패 양쪽 모두 **try-finally에서 If-Match 조건부 삭제**한다(14장 개인정보처리방침, 17장 파일 보안).<br>실패 task에도 ETag를 보존해 재시도하며, ETag 불일치 시 덮어쓴 새 객체는 파싱·삭제하지 않는다.<br>삭제 실패가 파싱 성공 응답을 막지는 않지만 반드시 마스킹 로그를 남긴다. |
| 캐시 만료(30일) | 매일 자정 배치로 만료된 `DONE` Resume의 `extractedText`를 삭제하고 `parseStatus=EXPIRED`로 전환한다(NFR-14). 레코드·면접 히스토리는 유지하고 업로드 슬롯에서는 제외한다. 배치 실패 시 다음 주기에 재시도한다(멱등 bulk update이므로 별도 복구 작업 불필요). |

## 2. LLM 응답 실패 (② 면접 엔진 + LLM)

- **JSON 스키마 검증 실패**: 최대 **1회 재요청**. 2회째(=1회 재요청 실패) 실패 시
  세션을 실패 상태로 전이하고, 사용자에게 "질문 생성/채점에 실패했습니다. 다시
  시도해주세요" 같은 명확한 안내를 반환한다(NFR-05). 조용히 빈 배열이나 기본값을
  반환하지 않는다.
- **내부 채점 요청 검증 실패**: 중복·범위 밖 questionId, 질문·예상답변 누락은 동일 요청으로
  재시도해도 복구되지 않으므로 `LlmSchemaValidationException` 재시도 대상에 포함하지 않는다.
  LLM이 반환한 응답 스키마 이탈과 호출 전에 발견한 내부 계약 위반을 구분한다.
- **점수 클램핑**: LLM이 범위 밖 점수(문항당 0~20 초과, 총점 0~100 초과)를 반환해도
  서버에서 반드시 clamp한다. clamp는 ③(최용성)의 책임이며, ②는 원시값을 그대로
  넘긴다(`docs/ai/owners/kim-hanbi.md`/`choi-yongseong.md` 경계 참고).
- **LLM 타임아웃**: 폴링 + 재시도로 대응한다(`docs/adr/ADR-004-polling-over-sse.md`).
  데모 당일에는 사전 워밍업 호출을 권장한다(12장 리스크 대응).
- **키워드-이력서 내용 불일치**: 이력서에 없는 기술 스택을 사용자가 키워드로 선택한
  경우, 프롬프트에 "관련 내용이 부족하면 일반적인 CS 지식 관점에서 질문하라"는 폴백
  지시를 포함한다(NFR-12). 이 폴백을 제거하는 변경은 반드시 이 문서를 먼저 갱신한다.
- **질문 난이도 편차**: 완전한 균일화는 근본적으로 불가능하다는 것을 팀이 인지하고
  있다(12장). 프롬프트에 난이도 가이드라인을 명시해 편차를 줄이는 정도로만 대응한다
  (NFR-10). "편차 0"을 목표로 삼지 않는다.

## 3. 인증 실패 (④ 인증)

- OAuth2 인증 실패: `401` 응답.
- Refresh Token 만료: 재로그인 유도. 만료된 Refresh Token으로 재발급을 시도하면
  `401`을 반환하고, 클라이언트는 로그인 화면으로 리다이렉트한다.
- Refresh Token은 자동 재발급 + **로테이션**한다 — 재발급 시마다 이전 토큰을 즉시
  무효화한다(재사용 탐지, `docs/ai/owners/pyo-jimin.md` 체크리스트).

## 4. 일정/배포 리스크 대응 (기획서 12장, 참고용)

이 절은 코드 레벨 실패 처리가 아니라 프로젝트 운영 리스크 대응 방안입니다. 팀 전체가
알고 있어야 하므로 여기 기록합니다.

| 리스크 | 대응 방안 |
| --- | --- |
| 3주차 통합 지연 | 1주차 API 계약 선확정 + 금요일 시연 + 레벨2(과장) 컷 → 레벨1(대리)만으로 데모 성립 |
| 프론트 일정 지연 | 필수 5화면 폴백 — 나머지는 전부 선택(FR-07) |
| 도메인 코드 고립 | PR 머지 전 1인 승인으로 강제 크로스 리뷰(`docs/ai/SHARED.md` §4-3) |
| 배포 실패 | 로컬 데모 폴백 기본 준비 |
| 4주차 개발 침범 | 3주차 종료 시 기능 동결(Feature Freeze), 미완 기능은 확장 계획으로 전환 |
