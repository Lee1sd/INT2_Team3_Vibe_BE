# harness-engineering-101.md — AI 코딩 하네스, 처음부터 쉽게

> 이 문서는 "하네스 엔지니어링이 뭔지 하나도 모르겠다"는 사람을 위한 문서입니다.
> 어려운 말 없이 쉽게 설명하고, 그다음 우리 프로젝트에서 실제로 어떻게 쓰는지,
> 규칙을 고치고 싶을 때 어떻게 건의하는지까지 순서대로 설명합니다. 다른 모든
> `docs/ai/*.md` 문서보다 **먼저** 읽는 문서입니다.

## 1. 하네스(harness)가 뭔가요? (비유로)

강아지 산책시킬 때 목줄(harness)을 채우는 걸 생각해보세요. 목줄이 있으면 강아지가
아무 데나 뛰어가지 않고, 산책하는 사람도 강아지를 매번 붙잡으러 뛰어다니지 않아도
됩니다. 강아지는 여전히 자기 발로 걷지만, 정해진 방향에서만 자유롭게 움직입니다.

**AI 코딩 에이전트(Claude Code)한테 채우는 목줄이 "AI 에이전트 하네스"입니다.**

AI는 코드를 아주 빠르게 잘 씁니다. 하지만 문제가 하나 있습니다: **AI는 대화가
끝나면 방금 배운 걸 전부 잊어버립니다.** 어제 "우리 프로젝트는 이런 규칙으로
개발한다"고 알려줘도, 오늘 새로 대화를 시작하면 AI는 그걸 기억하지 못합니다.
사람도 마찬가지입니다 — 3주 뒤, 3개월 뒤에 이 코드를 다시 보면 "왜 이렇게
만들었지?"를 기억 못 합니다.

그래서 우리는 **AI와 사람이 매번 다시 읽을 수 있는 "규칙 문서 + 자동으로 그
문서를 보여주는 장치"**를 만들어둡니다. 이게 하네스 엔지니어링입니다. 정리하면:

> **하네스 엔지니어링 = "이 프로젝트는 이렇게 만든다"는 규칙을 문서로 적어두고,
> AI가 매번 그 문서를 보게 만드는 자동화 장치를 같이 만드는 일.**

## 2. 왜 이게 "가장 중요한 근간"인가요?

4명이서 3주 동안 개발합니다. 그런데:

- 표지민 님이 만든 로그인 규칙을, 최용성 님이 몰라서 다르게 구현하면 → 나중에
  합칠 때 다시 뜯어고쳐야 합니다.
- AI에게 "레벨 해금 API 만들어줘"라고 시켰는데, AI가 요구사항명세서를 안 보고
  마음대로 필드명을 지으면 → 프론트가 붙지 않습니다.
- 3주 뒤 발표 준비하면서 "이 코드 왜 이렇게 짰지?"를 아무도 기억 못 하면 →
  설명을 새로 지어내야 합니다(그리고 대부분 틀립니다).

이 세 가지 문제의 공통 원인은 하나입니다: **"규칙이 어딘가에 있긴 한데, 필요한
순간에 아무도(사람도 AI도) 그걸 안 보고 있다."** 하네스 엔지니어링은 이 문제를
"규칙을 어디에 적을지 정하고, 필요한 순간에 자동으로 보여주기"로 해결합니다.

## 3. 우리 하네스는 어떻게 생겼나요? (구조)

우리 하네스는 4단계 서랍처럼 되어 있습니다. 아래로 갈수록 "더 자세하고, 덜 자주
필요한" 내용입니다.

```
1단계  CLAUDE.md            "뭘 봐야 하는지"만 알려주는 안내판 (규칙 본문 없음)
          │
2단계  docs/ai/SHARED.md    팀 전체 공통 규칙 (Git 컨벤션, 6단계 사고절차, 체크리스트)
          │  ← 세션 시작하면 자동으로 나타남 (사람이 아무것도 안 해도 됨)
          │
3단계  docs/ai/owners/*.md  "나"만 볼 규칙 (내가 건드릴 수 있는 코드 경로, 체크리스트)
          │  ← 자동으로 안 나타남. 세션마다 내가 직접 @로 불러야 함
          │
4단계  docs/requirements/*, docs/api/*, docs/erd/*, docs/adr/*, docs/state/*, docs/operations/*
       설계 문서 (필요한 절만 골라서 읽음, owner 파일이 "언제 이걸 봐야 하는지" 알려줌)
```

왜 4단계로 나눴을까요? **매번 전부 다 읽으면 AI도 사람도 지칩니다.** 1단계는
항상 보고, 2단계는 자동으로 보고, 3단계는 딱 내 몫만 보고, 4단계는 필요할 때만
찾아봅니다. 이렇게 하면 "봐야 하는데 안 본 규칙"이 줄어듭니다.

> 더 자세한 설계 근거(왜 FANDROPS 하네스에서 이 구조를 가져왔는지)는
> [`docs/adr/ADR-002-ai-agent-harness-engineering.md`](../adr/ADR-002-ai-agent-harness-engineering.md)에
> 있습니다. 이 문서는 "왜"보다 "어떻게 쓰는지"에 집중합니다.

## 4. 실제로 개발할 때 이걸 어떻게 씁니다 (하루 일과 예시)

이건희 님이 "이력서 재업로드 시 기존 파일 교체" 기능을 만든다고 해봅시다.

1. **Claude Code를 켠다.** → `SessionStart` 훅이 `docs/ai/SHARED.md`를 자동으로
   AI 컨텍스트에 넣어줍니다. 이건희 님은 아무것도 안 해도 됩니다.
2. **`@docs/ai/owners/lee-geonhui.md`를 직접 멘션한다.** → 이건 자동으로 안
   되므로 꼭 직접 해야 합니다. 이 파일에 "내가 건드릴 수 있는 경로", "건드리면
   안 되는 경로", "지금 봐야 할 설계 문서 목록", "체크리스트"가 다 있습니다.
3. **owner 파일의 "추가 필수 참조" 표를 보고 필요한 문서만 편다.** 이 경우
   `docs/requirements/functional-requirements.md`의 FR-01,
   `docs/erd/entity-definition.md`의 `Resume` 엔티티만 보면 됩니다. 19장짜리
   기획서를 처음부터 다시 읽지 않습니다.
4. **AI에게 시킨다.** AI는 `SHARED.md`의 6단계 사고 절차(Brainstorm → Plan →
   Execute → 역방향 추적 6문항 → Debug → Retro)를 따라 코드를 짭니다.
5. **커밋 전에 역방향 추적 6문항을 스스로 확인한다.** (`SHARED.md` §3) "DB
   제약이 실제로 있나?", "예외 처리가 되나?" 같은 질문에 전부 답할 수 있어야
   커밋합니다.
6. **커밋 → 브랜치 → PR.** `docs/ai/SHARED.md` §4의 Git 컨벤션(브랜치명, 커밋
   접두사)을 따르고, `docs/ai/workflows/auto-pr.md` 순서대로 PR을 올립니다.
7. **세션을 마치기 전에 `[Retro]` 한 줄을 출력한다.** (`SHARED.md` §5) — 이번
   작업에서 하네스 규칙이 실제로 도움이 됐는지, 뭘 고치면 좋을지 한 줄로 남깁니다.

이 7단계에서 이건희 님이 "직접" 한 일은 2번(owner 파일 멘션)뿐입니다. 나머지는
문서가 미리 정해둔 대로 자동/반자동으로 흘러갑니다.

## 5. Claude Code로 "문서 자동화"는 정확히 어떻게 하고 있나요?

"자동화"라고 부르는 건 크게 두 갈래입니다. 하나는 **훅**(사람이 아무것도
안 해도 정해진 순간에 저절로 실행), 다른 하나는 **스킬**(자연어로 요청하면
AI가 스스로 불러와 실행)입니다.

### 훅 — 4가지, 전부 `.claude/hooks/` 폴더의 파이썬 스크립트

`.claude/settings.json`에 "언제 실행할지"가 등록되어 있습니다.

| 훅 이름 | 언제 실행되나 | 무슨 일을 하나 |
| --- | --- | --- |
| `session-context.py` | 세션을 새로 시작할 때(`SessionStart`) | `docs/ai/SHARED.md` 전체를 AI 컨텍스트에 자동으로 넣어줌. 사람이 `@SHARED.md`를 매번 입력할 필요가 없어짐 |
| `llm-json-guard.py` | AI가 파일을 수정한 직후(`PostToolUse`), 그 파일이 LLM 연동 경로(`interview/`, `judgment/`, `progress/`, `persona/`, `prompts/`)일 때 | "LLM 응답이 깨지면 어떻게 처리하는지 확인했나?" 체크리스트를 다시 보여줌. 코드를 막지는 않음(참고만 하라는 뜻) |
| `retro-reminder.py` | AI 턴이 끝날 때(`Stop`), 브랜치가 `feat/*`/`fix/*`일 때 | AI가 이미 `[Retro]`를 출력했으면 그걸 찾아서 `retro-raw.md`에 자동 저장. 안 냈으면 "지금 `[Retro]` 한 줄 남겨야 한다"를 상기시켜줌 |
| `adr-suggestion.py` | 코드 수정 직후, 또는 `gh pr create`/`gh issue create`를 실행하려고 할 때 | "이 변경, ADR로 남겨야 할 결정 아닌가?"를 상기시켜줌 (§7 참고) |

### 스킬 — 2가지, `.claude/skills/` 폴더의 `SKILL.md`

훅과 다르게 스킬은 **사람(또는 AI)이 자연어로 요청해야 시작됩니다.**

| 스킬 이름 | 언제 쓰나 | 무슨 일을 하나 |
| --- | --- | --- |
| `new-issue` | "이슈 올려줘" 등 요청 시 (또는 `/new-issue`) | 기능/버그 템플릿을 채우고, 담당자 확인 후 `gh issue create` 실행 |
| `new-pr` | "PR 올려줘" 등 요청 시 (또는 `/new-pr`) | 실제 diff를 근거로 PR 템플릿을 채우고, 셀프 리뷰·ADR 확인 후 `gh pr create` 실행 |

**중요한 오해 하나**: 이 훅들은 코드를 "막지" 않습니다. 전부 "참고하라"고 알려주는
역할만 합니다(비차단성 훅). AI가 체크리스트를 무시하고 계속 진행할 수도 있습니다 —
그래서 6번(커밋 전 역방향 추적)처럼 **사람이 마지막에 확인하는 단계가 여전히
필요**합니다. 훅은 "잊지 않게 도와주는 장치"이지 "강제로 지키게 하는 장치"가
아닙니다.

또 다른 자동화는 **템플릿 + 스킬**입니다. 이슈/PR을 만들 때마다 빈 양식을 처음부터
채우지 않고, `docs/ai/workflows/templates/*.md`에 미리 만들어둔 틀을 복사해서
채운 뒤 `gh issue create --body-file ...` / `gh pr create --body-file ...`로
올립니다. 이 "복사해서 채우고 gh로 올리는" 절차 자체를 `.claude/skills/new-issue/`,
`.claude/skills/new-pr/` 두 스킬로 만들어뒀기 때문에, 그냥 **"이슈 올려줘" /
"PR 올려줘"라고 자연어로 말하면 AI가 알아서 이 스킬을 불러와 틀을 채우고, 실제로
올리기 전에 채운 내용을 보여주며 확인을 받습니다.** (`/new-issue`, `/new-pr`처럼
직접 호출할 수도 있습니다.) 자세한 순서는
[`docs/ai/workflows/auto-pr.md`](workflows/auto-pr.md), 스킬 동작 원리와 검증
상태는 [`docs/ai/setup-rules.md`](setup-rules.md) §7을 보세요.

## 6. 하네스 규칙을 고치고 싶을 때 — "건의"는 어떻게 하나요?

가장 많이 헷갈리는 부분입니다. 상황을 3가지로 나눠서 설명합니다.

### 상황 A. "내 담당 파일(owner 파일)만 고치면 되는 경우"

예: 최용성 님이 개발하다 보니 "체크리스트에 이 항목이 빠져 있었네" 싶은 게
있었다. → **그냥 `docs/ai/owners/choi-yongseong.md`를 고치고, 다른 변경과
똑같이 커밋 → PR 올리면 됩니다.** 이 파일은 최용성 님 "소유"이므로 특별한 절차가
필요 없습니다. 단, PR은 여전히 1인 승인을 받아야 머지됩니다(`SHARED.md` §4-3) —
왜 이 항목을 추가했는지 PR 설명에 한 줄만 적으면 리뷰어가 쉽게 판단할 수 있습니다.

### 상황 B. "팀 전체 공통 규칙(`SHARED.md`)을 고치고 싶은 경우"

예: "역방향 추적 체크리스트에 항목을 하나 더 추가하고 싶다", "Git 커밋 접두사를
바꾸고 싶다". → 이건 4명 모두에게 영향을 주므로, 다음 순서를 따릅니다.

1. **먼저 `[Retro]` 한 줄로 남긴다.** 세션을 마칠 때 "튜닝 제안" 칸에 적습니다
   (`SHARED.md` §5). 이게 "건의"의 1차 접수창입니다 — 거창하게 회의를 잡지
   않아도, 그냥 그날 세션에서 한 줄 남기는 것만으로 건의가 시작됩니다. `feat/*`/
   `fix/*` 브랜치라면 이 한 줄을 `retro-reminder.py`가 자동으로 개인 로컬
   `retro-raw.md`에 쌓아두므로, 나중에 채팅 기록을 뒤져서 찾을 필요가 없습니다.
2. **금요일에 4명 각자의 `retro-raw.md`를 공유하고, 한 명이
   `docs/ai/workflows/templates/retro-week-body.md` 템플릿으로 카테고리별
   (룰 작동/튜닝 제안/SSOT 동기화/Edge Case) 분류·중복 제거해서
   `docs/ai/workflows/generated/retro-week{N}.md` 1개 파일로 정리합니다.** 그냥
   시간순으로 이어붙이면 누구 건지도 안 보이고 뒤죽박죽 되니, "튜닝 제안" 표만
   보면 우선순위·제안자·반영 여부가 한눈에 보이게 정리합니다. 팀은 이 파일을
   보면서 짧게 논의합니다.
3. **반영하기로 하면 `SHARED.md`를 직접 고치고, 왜 고쳤는지 근거를**
   `docs/adr/ADR-002-ai-agent-harness-engineering.md`의 "결정 이력" 절에
   한 줄 추가합니다. (이 ADR이 "하네스 자체의 변경 기록부"입니다.)
4. 이것도 PR로 올리고 1인 승인을 받습니다 — 공통 규칙이라서 오히려 더
   신경 써서 리뷰합니다.

**즉, 건의 방법은 거창한 신청서가 아니라 "매 세션 끝 한 줄 + 금요일 5분 논의"**
입니다. 이 가벼움 자체가 하네스 설계 의도입니다(3주짜리 프로젝트에 무거운
프로세스를 얹으면 아무도 안 씁니다).

### 상황 C. "설계 문서(요구사항/API/ERD 등)를 고치고 싶은 경우"

예: 기획이 바뀌어서 FR-05 내용이 달라졌다. → 이건 하네스 규칙이 아니라
**프로젝트의 사실(fact)**이 바뀐 것이므로, 팀 전체 합의가 먼저 필요합니다.
합의되면 해당 문서(`docs/requirements/functional-requirements.md` 등)를 고치고,
그 문서를 참조하는 owner 파일들도 같이 확인합니다. 이 문서들은 "AI가 어떻게
행동할지"가 아니라 "우리가 뭘 만들기로 했는지"의 SSOT이기 때문입니다.

## 7. (신규) ADR 자동 감지 훅 — 코드/PR/이슈에서 "이거 ADR 아니야?"를 AI가 먼저 물어봄

ADR을 쓰는 습관 자체가 왜 중요한지, 어떻게 쓰는지는
[`docs/adr/how-to-write-adr.md`](../adr/how-to-write-adr.md)를 보세요. 이 절은
**자동화 부분만** 설명합니다.

`.claude/hooks/adr-suggestion.py`가 다음 두 순간에 동작합니다.

1. **코드 수정 직후**: 빌드 설정(`build.gradle.kts` 등), 배포/CI 설정
   (`Dockerfile`, `.github/workflows/**`), 전역 설정(`global/config/**`,
   `application.yml`)처럼 "구조적 결정"이 잘 일어나는 파일을 고쳤거나, 수정한
   내용 안에 "선택", "대안", "트레이드오프", "채택", "vs", "반려" 같은 결정을
   암시하는 단어가 있으면 → "이 변경, ADR로 남길 결정인가요?"라는 안내를
   AI 컨텍스트에 띄웁니다.
2. **`gh pr create` / `gh issue create`를 실행하려는 순간**: 실행 직후 "PR/이슈를
   올리기 전에 ADR이 필요한 변경인지 한 번 더 확인하라"는 안내를 띄웁니다.

이 훅도 다른 훅과 마찬가지로 **막지 않고 알려만 줍니다.** 진짜 ADR이 필요한지는
사람(또는 AI가 판단해서 사용자에게 물어보는 방식)이 최종 결정합니다. 오탐(별거
아닌 변경인데 계속 알림이 뜨는 것)이 너무 잦으면, 이 훅의 키워드/경로 목록을
`docs/ai/setup-rules.md`에 검증 결과를 남기고 좁혀 나가세요 — 이것도 §6 상황 B
방식(Retro → 반영)으로 튜닝합니다.

## 8. 요약 (한 문단)

하네스 엔지니어링은 "AI와 사람이 매번 다시 봐야 하는 규칙을 문서로 못박고, 그
문서를 필요한 순간에 자동으로 보여주는 장치를 같이 만드는 것"입니다. 우리는 이걸
4단계 문서(진입점 → 공통 규칙 → 개인 규칙 → 설계 문서), 4개의 훅(세션 시작
자동 주입, LLM 방어 리마인드, Retro 리마인드, ADR 감지), 2개의 스킬(이슈 생성,
PR 생성 자동화)으로 구현했습니다. 규칙을 고치고 싶으면 거창한 절차 대신 "세션 끝
`[Retro]` 한 줄 → 금요일 논의 → 반영 + ADR-002에 근거 기록"이라는 가벼운 루프를
씁니다. 이 루프가 계속 돌면 하네스는 프로젝트가 끝날 때까지 점점 더 우리 팀에
맞게 다듬어집니다.
