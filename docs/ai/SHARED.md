> 오래된 세션을 이어가는 경우를 대비해, 이 문서는 사람이 읽어도 완결된 내용이어야 합니다.

## 1. 대화 시작 시 확인 순서

1. 이 문서(SHARED.md)는 이미 주입되어 있습니다. 다시 요청하지 마세요.
2. 본인 owner 파일을 `@docs/ai/owners/<본인 이름>.md`로 멘션하세요. (자동 주입되지 않습니다)
3. 작업 대상 코드 경로가 `docs/ai/README.md`의 "경로 → 오너" 표와 일치하는지 확인하세요.
   본인 담당이 아닌 경로를 수정해야 한다면, 먼저 그 owner에게 알리거나 팀 채널에 공지하세요.

## 2. 6단계 사고 절차

모든 기능 구현·버그 수정 작업은 아래 순서를 따릅니다. 순서를 건너뛰지 마세요.

1. **Brainstorm** — 요구사항명세서(FR/NFR)와 API 명세서에서 관련 항목을 찾고, 가능한 접근을
   최소 2가지 이상 떠올립니다. LLM을 호출하는 기능이라면 "Mock 모드에서 어떻게 동작할지"를
   먼저 정의합니다.
2. **Plan** — 변경할 파일 목록, 엔티티/DDL 영향, API 응답 계약 변경 여부를 문장으로 먼저
   적습니다. 표지민이 확정한 공통 응답 포맷/예외 계약을 벗어나지 않는지 확인합니다.
3. **Execute** — 계획한 범위만 구현합니다. 담당 owner 파일의 "손대지 말 것" 경로는
   건너뛰고, 필요하면 해당 owner에게 요청합니다.
4. **역방향 추적 자가검증 (6문항)** — 아래 §3의 6개 질문에 전부 답할 수 있어야 커밋합니다.
5. **Debug** — 실패하면 재현 조건을 먼저 문장으로 적고, 관련 로그/스택트레이스를 확인한
   뒤 수정합니다. 추측성 수정을 반복하지 않습니다.
6. **Retro** — 작업이 끝나면 §5 형식의 `[Retro]` 한 줄을 출력합니다.

## 3. 역방향 추적 체크리스트 (6문항)

FANDROPS의 4문항(Spring Boot 공통)을 유지하고, Career Dungeon 특화 리스크 2개(⑤⑥)를 추가한
버전입니다. 이 프로젝트가 실제로 겪는 결함을 보고 항목을 추가/수정하면 그 자체가 §6 Retro
루프의 결과물입니다.

| # | 질문 | 확인 방법 | 근거 |
| --- | --- | --- | --- |
| ① DB 제약 | 이 변경이 요구하는 제약(UNIQUE, FK, NOT NULL 등)이 실제 DDL/엔티티에 있는가? | 엔티티 클래스와 `docs/erd/entity-definition.md` 대조 | 엔티티정의서 |
| ② 예외 핸들러 | 새로 던지는 예외가 어떤 `@ExceptionHandler`/`@RestControllerAdvice`에서 잡히는가? | `global.exception` 패키지 grep | Spring Boot 공통 |
| ③ 직렬화 설정 | `Instant`/점수/열거형 필드의 직렬화 결과가 API 명세서의 응답 예시와 정확히 일치하는가? | `application.yml`, 실제 JSON 응답 확인 | Spring Boot 공통 |
| ④ 테스트 파일 | 새 Service/Client/Controller에 대응하는 테스트가 있는가? | `src/test/java/...` 확인 | Spring Boot 공통 |
| ⑤ LLM 응답 방어 | 이 코드가 호출/소비하는 LLM 응답이 스키마를 벗어나면(필드 누락, 점수 범위 초과) 어떻게 되는가? Mock 모드에서도 동일 분기가 동작하는가? | `LlmClient` 인터페이스의 예외/재시도 경로 추적 | NFR-05, NFR-12 |
| ⑥ 비용/시간 가드 | 이 코드가 LLM을 호출한다면 예산 상한·타임아웃·재시도 횟수 제약을 지키는가? | `docs/operations/llm-cost-policy.md` 대비 확인 | NFR-11 |

담당 도메인이 LLM을 직접 호출하지 않는다면(예: `resume`, `auth`) ⑤⑥은 "해당 없음"으로 명시하고
넘어가도 됩니다. 단, 명시적으로 "해당 없음"이라고 말해야 합니다 — 조용히 건너뛰지 않습니다.

## 4. Git / 협업 컨벤션 (팀 확정, 아래 4가지가 SSOT)

1. **브랜치 전략**: `main` / `feat/{이슈번호}-{기능명}` / `fix/{이슈번호}-{내용}`
   (예: `feat/23-resume-upload`, `fix/31-parse-status-null`). `main`에 직접 커밋하지 않습니다.
2. **커밋 컨벤션**: 커밋 메시지 접두사는 아래 6종만 사용합니다. 형식은
   `<type>: <한 줄 요약>` (예: `feat: 이력서 업로드 API 추가`).
   | type | 용도 |
   | --- | --- |
   | `feat` | 새 기능 |
   | `fix` | 버그 수정 |
   | `refactor` | 동작 변경 없는 구조 개선 |
   | `docs` | 문서 변경 (이 저장소의 `docs/`, `CLAUDE.md` 등) |
   | `test` | 테스트 추가/수정 |
   | `chore` | 빌드/설정/의존성 등 그 외 |

   접두사 뒤에는 "무엇을"보다 "왜"를 남깁니다. "무엇을"은 diff로 충분한 경우 생략합니다.
3. **PR 규칙**: **최소 1인 리뷰 승인 후 머지**합니다. 승인 없이 머지하지 않습니다
   (기획서 12장 "도메인 코드 고립" 리스크 대응 — PR 머지 전 1인 승인으로 크로스 리뷰를
   강제해 도메인 간 경계 침범/누락을 조기에 잡습니다). PR 본문은
   `.github/PULL_REQUEST_TEMPLATE.md`를 그대로 사용합니다. AI가 초안을 만들 때는
   `docs/ai/workflows/templates/pr-body.md`를 채워서 `gh pr create --body-file`로 생성합니다.
   PR을 올리기 전 셀프 리뷰, CodeRabbit(AI)과 사람 리뷰의 역할 분담, 코멘트 이모지
   룰은 `docs/ai/workflows/code-review-culture.md`가 SSOT입니다.
4. **이슈 트래킹**: 작업 단위는 GitHub Issues로 관리합니다. 이슈를 만들 때 **담당자
   (assignee)를 반드시 지정**합니다 — 담당자 없는 이슈로 작업을 시작하지 않습니다.
   템플릿은 `.github/ISSUE_TEMPLATE/feature.md` 또는 `bug.md`를 사용합니다. 브랜치명의
   `{이슈번호}`는 이 이슈 번호와 반드시 일치해야 합니다.

공통 응답 포맷/예외 계약은 표지민이 1주차 중 확정합니다. 확정 전까지는 임시 계약임을
PR에 명시하고, 확정 후에는 반드시 맞춰서 수정합니다 (요구사항명세서 CM-002 참고).

## 5. Retro 형식 (경량화 버전)

FANDROPS는 PR마다 `generated/retro-<PR번호>.md`를 쌓았지만, 3주짜리 프로젝트에는
과합니다. Career Dungeon은 다음 3단계로 경량화합니다.

1. **세션 종료 시**: 아래 형식으로 대화창에 한 줄만 출력합니다.

   ```
   [Retro] 룰 작동: <이번에 하네스 규칙이 실제로 도움이 됐는지>
          | 튜닝 제안: <SHARED.md/owner 파일에 추가·수정하면 좋을 항목>
          | SSOT 동기화 필요: <설계 문서와 실제 코드가 어긋난 부분이 있었는지>
          | Edge Case: <이번 작업에서 새로 발견한 예외 상황>
   ```

   `feat/*`/`fix/*` 브랜치에서는 이 출력을 `.claude/hooks/retro-reminder.py`가
   감지해서 **자동으로** `docs/ai/workflows/generated/retro-raw.md`(개인 로컬 파일,
   커밋 안 함)에 날짜·브랜치와 함께 append합니다. 따로 파일에 저장할 필요는
   없지만, 반드시 이 형식 그대로 출력해야 훅이 인식합니다 — 형식을 바꾸면 자동
   수집이 안 되고 사람이 채팅 기록에서 직접 찾아야 합니다.
2. **매주 금요일**: 4명 각자의 `retro-raw.md`를 공유하고, 한 명이
   `docs/ai/workflows/templates/retro-week-body.md` 템플릿에 맞춰 **카테고리별로
   분류·중복 제거해서** `docs/ai/workflows/generated/retro-week{N}.md` 1개 파일로
   압축합니다 (시간순으로 그냥 이어붙이지 않습니다 — 자세한 절차는
   `docs/ai/workflows/generated/README.md` 참고, 4주 프로젝트라면 최대 파일 4개).
3. **반영**: 압축본에서 반영하기로 한 개선사항은 다음 주 시작 전
   `SHARED.md`/`owners/*.md`에 바로 반영하고, 반영 근거를 ADR 1개로 남깁니다
   (`docs/adr/ADR-002-ai-agent-harness-engineering.md`의 "결정 이력" 절에 추가).

## 6. 절대 규칙

- LLM을 직접 호출하는 새 코드를 작성하기 전에는 반드시 Mock 구현체로 먼저 동작을 확인합니다.
- `LlmClient` 인터페이스를 거치지 않고 특정 벤더 SDK를 도메인 코드에서 직접 참조하지 않습니다.
- 점수·게이지 값은 서버에서 항상 clamp합니다. LLM이 범위 밖 값을 반환해도 그대로 저장하지 않습니다.
- `docs/ai/owners/`를 "AI 면접관 페르소나" 설정으로 착각하지 않습니다. 그건 `domain.persona`입니다.
- 담당이 아닌 owner의 "손대지 말 것" 경로를 임의로 수정하지 않습니다.
- 구조적 결정(대안 검토, 다른 도메인에 영향)을 코드로만 남기고 넘어가지 않습니다.
  `docs/adr/how-to-write-adr.md` §3 기준에 해당하면 ADR을 씁니다 — 미래의 우리는
  지금의 대화를 기억하지 못합니다.
