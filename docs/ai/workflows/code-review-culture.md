# code-review-culture.md — 코드 리뷰 문화 (AI 리뷰 + 사람 리뷰)

> 우리는 PR을 올리면 CodeRabbit(AI)이 자동으로 1차 리뷰를 남기고, 그 후 팀원 1명
> 이상이 승인해야 머지합니다(`docs/ai/SHARED.md` §4-3). 이 문서는 "AI 리뷰와
> 사람 리뷰를 어떻게 나눠 쓸지", "PR을 올리기 전/리뷰할 때 무엇을 지킬지"의
> SSOT입니다.

## 1. AI 코드 리뷰의 한계 — 왜 CodeRabbit이 전부를 대체할 수 없나

AI 리뷰어(CodeRabbit)는 코드만 보고 판단합니다. 하지만 좋은 리뷰는 코드뿐 아니라
"이 팀이 왜 이렇게 만들기로 했는지"까지 알아야 합니다. 예를 들어:

- CodeRabbit은 `progressGauge`에 `+40`을 더하는 코드를 보고 버그라고 지적할 수
  있습니다. 하지만 `docs/requirements/open-questions.md` #3(마지막 레벨은 +30이
  아니라 +40일 수 있음)을 모르면, 이게 **의도된 값**인지 판단할 수 없습니다.
- CodeRabbit은 "이 API가 `IS-002`/`IS-002b` 명세와 정확히 같은 필드명을 쓰는지"는
  비교적 잘 잡아낼 수 있지만, "이 뱃지 Stage 매핑이 기획 의도와 맞는지"(FR-09,
  Stage 해석 문제)처럼 **여러 문서를 종합해야 하는 판단**은 하기 어렵습니다.

즉, **AI는 도메인(비즈니스) 컨텍스트를 100% 이해할 수 없기 때문에, AI 리뷰가
사람 리뷰를 완전히 대체할 수 없습니다.**

## 2. 역할 분담: AI는 보안/성능, 사람은 로직/도메인

아래 표대로 역할을 나눕니다. 리뷰할 때 "이건 어차피 CodeRabbit이 잡아줄 것"이라고
사람이 건너뛰어도 되는 항목과, "이건 사람이 반드시 봐야 하는" 항목을 구분하는
용도입니다.

| 영역 | 주 담당 | 왜 |
| --- | --- | --- |
| 보안 취약점 (SQL 인젝션, 시크릿 하드코딩, 인증/인가 누락) | 🤖 AI | 패턴이 명확하고 기계적으로 잘 잡힘 |
| 성능 이슈 (N+1 쿼리, 불필요한 반복문, 인덱스 누락) | 🤖 AI | 코드 패턴만 봐도 감지 가능 |
| 코드 스타일/컨벤션 (네이밍, 불필요한 코드) | 🤖 AI | 규칙 기반이라 AI가 빠르고 정확함 |
| 비즈니스 로직이 요구사항(FR/NFR/API 명세)과 맞는가 | 🙋 사람 | 도메인 문서를 종합적으로 알아야 함 |
| 도메인 경계 침범 여부 (`docs/ai/README.md` 경로→오너 표) | 🙋 사람 | "이 코드가 남의 담당 영역을 건드렸는가"는 팀 맥락을 알아야 판단 |
| SSOT 불일치 항목과의 연관성 (`docs/requirements/open-questions.md`) | 🙋 사람 | 문서 여러 개를 엮어서 봐야 함 |
| ADR로 남겨야 할 결정인지 | 🙋 사람 (+ `adr-suggestion.py` 훅이 리마인드) | 판단 자체가 사람의 몫, 훅은 상기시켜주기만 함 |

**리뷰어는 CodeRabbit 코멘트를 무시하지 않습니다** — 보안/성능 코멘트는 특별한
이유가 없으면 반영합니다. 다만 CodeRabbit이 "문제"라고 표시해도, 팀 문서(특히
`open-questions.md`)에 근거가 있는 의도된 값이면 PR 코멘트로 그 근거를 링크해
답변하고 넘어갑니다 — 조용히 무시하지 않습니다.

## 3. 올바른 리뷰 문화

### 3-1. PR 올리기 전 셀프 리뷰는 필수입니다

PR을 올리기 전에 본인이 먼저 diff를 처음부터 끝까지 한 번 읽습니다. 확인할 것:

- [ ] 디버깅용 로그, 주석, 죽은 코드가 남아있지 않은가
- [ ] `docs/ai/SHARED.md` §3 역방향 추적 6문항에 전부 답할 수 있는가
- [ ] 본인 owner 파일의 "손대지 말 것" 경로를 건드리지 않았는가
- [ ] PR 본문(`docs/ai/workflows/templates/pr-body.md` 기준)을 리뷰어가 맥락 없이
      읽어도 이해할 수 있게 채웠는가

셀프 리뷰를 건너뛰고 올린 PR은, 리뷰어가 "기본적인 것도 못 걸러졌다"고 느껴
불필요한 감정 소모를 만듭니다. 셀프 리뷰는 리뷰어를 위한 배려입니다.

### 3-2. 이모지 룰 (감정 소모 줄이기)

텍스트만으로는 "지적"인지 "제안"인지 "그냥 궁금해서 물어보는 것"인지 구분하기
어렵습니다. PR 코멘트를 남길 때 아래 접두사 이모지를 붙입니다.

| 이모지 | 의미 | 예시 |
| --- | --- | --- |
| 🔴 | 머지 전 반드시 수정 필요 (블로킹) | 🔴 이 API 응답 필드명이 `IS-002` 명세와 다릅니다 |
| 🟡 | 제안, 지금 안 고쳐도 머지 가능 | 🟡 이 부분은 나중에 상수로 분리하면 좋을 것 같아요 |
| 🔵 | 단순 질문, 답변만 필요 | 🔵 이 분기는 어떤 케이스를 방어하는 건가요? |
| 🟢 | 칭찬/동의, 답변 불필요 | 🟢 이 부분 깔끔하네요 |
| ❓ | 리뷰이(코드 작성자)가 리뷰어에게 되묻는 용도 | ❓ 이 코멘트는 CodeRabbit 오탐인 것 같은데 어떻게 생각하세요? |

- 🔴가 하나라도 남아있으면 approve하지 않습니다.
- 🟡/🔵는 답변만 하고 별도 커밋 없이 머지해도 됩니다(단, 답변은 반드시 남깁니다 —
  "확인했다"는 표시 없이 조용히 넘어가지 않습니다).
- CodeRabbit 코멘트에도 사람이 같은 이모지 룰로 후속 코멘트를 달아, "이건 반영했다
  /이건 의도된 값이라 반영 안 한다"를 명시적으로 남깁니다.

### 3-3. 리뷰 코멘트 작성 원칙

- **의도를 먼저 설명하고 지적한다.** "이거 틀렸어요"보다 "제가 이해하기로는
  ~인데, 이 경우엔 ~가 발생하지 않나요?"처럼 질문형으로 시작하면 오해가 줄어듭니다.
- **근거 문서를 링크한다.** "FR-05대로면 이 값이 아닌 것 같아요"처럼 구체적인
  문서/ID를 함께 남깁니다. 근거 없는 "그냥 이상해 보여요"는 피합니다.
- **사람 대 사람 리뷰에서는 코드가 아니라 사실(FR/API/ERD)에 근거해 논쟁한다.**
  의견이 갈리면 `docs/requirements/open-questions.md`에 항목을 추가하고, 팀
  전체가 볼 수 있게 합니다 — PR 코멘트 안에서 끝내지 않습니다.

## 4. PR 템플릿과의 연결

`.github/PULL_REQUEST_TEMPLATE.md`와 `docs/ai/workflows/templates/pr-body.md`의
체크리스트에 "셀프 리뷰 완료" 항목이 있습니다(§5 참고). 이 항목에 체크하지 않고
올린 PR은 리뷰어가 반려할 수 있습니다.

## 5. 주말 자가 머지 (예외 조건)

평일에는 반드시 팀원 1인 승인 후 머지합니다(`docs/ai/SHARED.md` §4-3).
주말(토·일)에는 아래 **4가지 조건을 모두 충족**할 경우에 한해 자가 머지를 허용합니다.

### 5-1. 조건 체크리스트

- [ ] **① 주말(토·일)** — 평일에는 이 예외를 적용하지 않습니다.
- [ ] **② 디스코드 알림 후 2시간 무응답** — PR을 올린 직후 Discord에서 해당 도메인
      담당자(`docs/ai/README.md` 경로→오너 표 기준)를 태그해 리뷰 요청을 남깁니다.
      2시간 이내 응답이 없을 때만 다음 단계로 넘어갑니다.
- [ ] **③ 타 도메인 영향 없음** — 아래 4항목 전부 해당해야 합니다:
  - 변경 파일이 전부 본인 `domain.*` 패키지 안에 있음
  - `global.*` 수정 없음
  - API 응답 계약(`ErrorResponse` 포함) 변경 없음
  - DB 스키마·엔티티 변경 없음
- [ ] **④ 셀프 리뷰 기록** — `/code-review` 결과 또는 §3-1 셀프 리뷰 체크리스트를
      PR 코멘트로 직접 남깁니다. "이상 없음"만 적는 것은 인정하지 않습니다.

### 5-2. 자가 머지 후 처리

- 머지 직후 팀 Discord 채널에 "주말 자가 머지 완료 — PR #번호"를 남깁니다.
- 다음 근무일 시작 전 팀원이 해당 PR을 비동기로 확인하고, 🔴 블로킹 이슈 발견 시
  즉시 이슈 또는 PR로 제기합니다.

> **이 예외 조건을 악용하지 않습니다.** "어차피 주말이니까"라는 이유만으로
> ③ 체크리스트에 해당하지 않는 변경을 자가 머지하는 것은 이 조건의 취지에 어긋납니다.
