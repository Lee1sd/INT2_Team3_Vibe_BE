# AI 하네스 트러블슈팅 기록

> `ai-experiment-log.md`에서 서비스 Claude API 활용 기록과 구분하기 위해 분리한 개발 과정 하네스/SSOT 트러블슈팅 기록입니다.
> 프롬프트, 모델 선택, 채점 기준 자체가 아니라 근거 검증, 리뷰 반영 방어, 도메인 경계와 호출 원칙 충돌을 다룹니다.

## 1. 모범답안 저장 구조 변경 지시 검증

| 단계 | 내용 |
|---|---|
| 발생 | 이후 "message_id 방식으로 정정하라"는 지시가 있었으나, Claude Code가 git 히스토리 전체를 검색한 결과 해당 결정의 근거가 저장소 어디에도 없음을 발견했다. 반면 기존 `session_id` 방식은 90분간 4단계 커밋으로 신중히 반영된 이력이 확인됐다. |
| 원인/근거 확인 | git 히스토리와 기존 문서/코드 근거를 확인했으나 `message_id` 방식이 이미 확정됐다는 저장소 근거는 찾지 못했다. 기존 `session_id` 방식은 실제 커밋 이력이 있어 즉시 폐기할 근거가 부족했다. |
| 조치/결정 | 근거 없이 SSOT를 변경하지 않고, 팀원(이건희·최용성) 직접 재확인을 거친 뒤에야 반영했다. AI가 그럴듯한 지시를 무비판적으로 실행하지 않고 근거를 요구한 사례로 남긴다. |

## 2. 리뷰 반영 중 정책 오염 방지 사례

| 단계 | 내용 |
|---|---|
| 발생 | 코드리뷰에서 "꼬리질문 생성이 어느 호출에 포함되는지 명확히 하라"고 지적받고 문서를 정리하는 과정에서, 기존 "세션당 최대 2회" 호출 상한이 별도 정책 결정 없이 "질문생성/최초채점/꼬리질문생성/최종채점" 4회 구조로 암묵 변경될 뻔함 |
| 발견 | 반영 직후 스스로 "이건 단순 문서 정리가 아니라 비용 정책 변경"임을 자각하고 커밋 전 중단/확인 요청 |
| 조치 | 이후 추가 코드 추적(5번)에서 현재 구현은 `LlmInvocationService` 기준 질문생성/최초채점/최종채점 3회뿐이고, 꼬리질문 생성 호출은 아직 없음을 재확인. 세션당 정상 호출 횟수는 현재 3회로 정정하고, 꼬리질문 생성 구현(#59) 후 4회로 재정합화하기로 함 |

## 3. 세션당 호출 횟수 원칙 재검증 (이후 현재 3회로 재정정)

| 단계 | 내용 |
|---|---|
| 발견 | 이슈 #50 논의 중 최초 추론으로 "질문생성/최초채점+꼬리질문생성/최종채점" 3단계(3회)가 물리적 최소 구조라고 판단 |
| 재검증 | 당시에는 judgment 쪽 최초채점+최종채점 2회, interview 쪽 질문생성+꼬리질문생성 2회로 나뉘었다고 판단했으나, 이후 5번 재검증에서 `LlmInvocationService`에 꼬리질문 생성 메서드가 없음을 확인했다. 현재 코드 기준 실제 정상 호출은 3회(재시도 최악 6회)이며, #59 구현 후 4회가 될 예정이다 |
| 교훈 | 논리적 추론(합칠 수 있는 조합)만으로 결론 내리지 않고, 실제 구현 코드를 직접 확인하는 것이 정확한 판단에 필수적임 |

## 4. 도메인 경계와 호출 원칙의 구조적 불일치 발견 및 최종 결정

| 단계 | 내용 |
|---|---|
| 발견 | 당시에는 세션당 정상 호출 횟수가 4회라고 보고 ②(interview: 질문/꼬리질문 생성)와 ③(judgment: 최초/최종 채점)의 도메인 분리 때문에 호출 통합이 어렵다고 판단했다. 이후 5번에서 현재 코드에는 꼬리질문 생성 호출 자체가 없음을 확인해, 현재 기준은 3회이고 #59 구현 후 4회로 변경 예정이라고 정정했다 |
| 검토한 대안 | A안(②가 최초채점+꼬리질문생성을 통합 호출, 도메인 인터페이스 재조율) vs B안(현재 구조 유지, 재시도 횟수만 축소) |
| 최종 결정 | B안 채택 — 재시도 최대 1회로 축소. 현재 코드 기준 최악 케이스는 6회, #59 구현 후 최악 케이스는 8회로 관리 |
| 근거 | A안은 이미 완성된 ②/③ 도메인 인터페이스를 재조율하는 작업이라 일정 리스크가 큼. Haiku 4.5가 저렴해 현재 6회 및 #59 구현 후 8회 호출도 $75 예산 대비 여유 있다고 판단 |
| 후속 조치 | 개발 중 Console에서 실제 API 사용량을 주기적으로 확인, 예산 소진 속도가 예상보다 빠르면 A안 재검토 |
| 교훈 | 확정된 정책(호출 횟수)과 확정된 아키텍처(도메인 경계)가 서로 독립적으로 결정되면, 실제 구현 단계에서 물리적으로 양립 불가능한 상황이 드러날 수 있음. 발견 즉시 근본 원인(A안)과 현실적 완화책(B안)을 함께 검토해 촉박한 일정에서도 리스크를 관리한 사례 |

## 5. "완료" 보고 이후 실제 코드 흐름 추적으로 발견한 기능 누락

| 단계 | 내용 |
|---|---|
| 발생 | ② 도메인(질문생성/채점 등) 전체가 "완료"로 이미 보고된 상태였으나, 이슈 #50(호출 횟수 재검증) 논의 중 `LlmInvocationService`의 실제 메서드 목록을 하나씩 추적하는 과정에서 이상 징후 발견 |
| 발견 | 질문생성/최초채점/최종채점 3개 메서드만 존재하고, "꼬리질문 생성"을 담당하는 별도 메서드가 없음을 확인. `evaluateFinalAnswers`는 꼬리질문 답변이 이미 주어진 것을 전제로 채점만 하도록 구현되어 있어, "누가 꼬리질문을 만드는지"가 코드 어디에도 없다는 게 드러남 |
| 검증 | 코드래빗 리뷰(호출 횟수 3회 vs 4회 불일치 지적)를 계기로 실제 코드를 직접 열어 메서드 목록을 확인, "말로 확인된 완료"와 "실제 코드 상태"가 다르다는 걸 재확인 |
| 확인 완료 | 최용성에게 "`evaluateFinalAnswers`는 꼬리질문 답변이 이미 주어진 것을 전제로 하는데, 그 꼬리질문을 만드는 코드가 interview 쪽에 없다"고 직접 알렸고, 최용성이 확인함. 꼬리질문 생성이 ②(interview) 담당임을 상호 확인하고 별도 이슈로 등록해 진행 |
| 조치 | PM에게 보고, 새 작업지시서로 "꼬리질문 생성" 기능을 별도 이슈 #59로 등록했다. 이후 PR #68로 구현되어 main에 반영 완료 |
| 교훈 | "도메인 완료" 보고가 실제로는 체크리스트 항목만 충족했다는 뜻일 뿐, 전체 기능 흐름을 코드 레벨까지 추적한 검증과는 다를 수 있음. message_id 검증 사례(1번)와 마찬가지로, AI가 사람의 보고/전달을 그대로 믿지 않고 코드베이스 자체를 직접 검증해 문제를 찾아낸 사례 |

## 8. raw weakestQuestionId 직접 사용 발견 및 재설계 (#73)

| 단계 | 내용 |
|---|---|
| 발생 | IS-002 답변 제출/채점 API 설계 전, 최초채점 → 꼬리질문 생성 흐름이 실제로 어디서 연결되는지 추적하는 과정에서 `InterviewService`가 LLM raw 응답의 `weakestQuestionId`를 직접 사용하고 있음을 발견 |
| 문제 | 원래 경계는 ②(`LlmInvocationService`)가 LLM을 호출해 raw JSON/응답을 받고, ③(`JudgmentScoringService`)이 점수 clamp, 총점 계산, 합격 여부, 최저점 문항 보정을 담당하는 구조였다. raw `weakestQuestionId`를 바로 꼬리질문 흐름에 쓰면 비정상 응답에서 raw 값과 보정 후 최저점 순위가 달라질 수 있음 |
| 조치 | 이슈 #73에서 `LlmInvocationService`를 평가 LLM 호출 단일 기준으로 통합하고, `InitialEvaluationResponse`/`FinalEvaluationResponse`를 judgment raw 모델로 변환하는 어댑터를 도입. 꼬리질문 생성은 ③이 보정한 `weakestQuestionId`를 받아 사용하도록 재설계 |
| 교훈 | "LLM 응답에 필드가 있다"는 사실과 "서비스 판단에 바로 써도 된다"는 결론은 다르다. raw 값은 호출 계층의 산출물이고, 서비스 판단값은 도메인 보정 계층을 통과한 뒤에만 사용해야 한다 |

## 9. ②/③ 경계 애매 항목 분류와 PM 판단

| 단계 | 내용 |
|---|---|
| 발생 | MockLlmClient와 InterviewService를 점검하면서 점수 재계산, 루브릭 보정, 최저점 선택처럼 ②(LLM 호출)와 ③(judgment 채점) 경계가 섞일 수 있는 로직을 별도로 분류 |
| 애매한 것1 | `InterviewService.java`의 raw `weakestQuestionId` 직접 사용. 최용성 확인 완료: 비정상 응답 시 raw 값과 보정값의 최저점 순위가 달라질 수 있어 제거/재설계 대상. #73에서 ③ 보정값을 받아 꼬리질문 흐름에 사용하는 구조로 정리 |
| 애매한 것2 | 점수 범위 0~25 검증(`MockLlmClient`, `LlmInvocationService`). PM 판단: 제거 대상 아님. ②가 LLM 응답 스키마와 숫자 범위를 검증하는 것은 호출 안정성 검증 영역으로 유지 |
| 애매한 것3 | MockLlmClient의 종합피드백용 최저점 선택 로직. PM 판단: ③ 판단 영역 침범이므로 제거 대상. 최저점 판단, 점수 합산, 합격 여부 판정은 judgment 쪽으로 이동해야 함 |
| 교훈 | 경계가 애매한 로직은 "계산을 한다/안 한다"가 아니라 "무엇을 검증하는가, 무엇을 판단하는가"로 나눠야 한다. 스키마·범위 검증은 호출 계층에 남길 수 있지만, 보정·합산·판정은 judgment 도메인으로 모아야 한다 |

## 10. EvaluationLlmClient 제거 및 어댑터 통합 (#78)

| 단계 | 내용 |
|---|---|

| 발견 | 해당 포트는 실 서비스 흐름에서 사용되지 않고 단위테스트 중심으로만 남아 있었으며, 별도 Mock 채점 응답 타입과 요청 타입이 ②/③ 경계를 다시 중복시키는 구조였음 |
| PM/담당 확인 | 최용성 확인 완료: 실 서비스 미사용, 단위테스트만 있음, 제거 승인 |
| 조치 | 이슈 #78에서 `EvaluationLlmClient`, `MockEvaluationLlmClient`, mock-only 요청 DTO를 제거하고, #73에서 만든 `LlmEvaluationResponseAdapter` 구조를 기준으로 judgment raw 모델 연결을 통합 |
| 교훈 | 새 경계(#73)를 만든 뒤에는 기존 포트가 단순히 "안 쓰이는 코드"인지, 아니면 과거 아키텍처를 다시 부활시킬 수 있는 중복 진입점인지 확인해야 한다. 미사용 포트는 테스트 편의보다 경계 혼선을 키울 수 있으므로 제거하는 것이 맞다 |

## 11. 처리 중 세션 상태 고착 가능성 발견 (#83 후속)

| 단계 | 내용 |
|---|---|
| 발생 | IS-002 답변 제출 API에서 중복 LLM 호출을 막기 위해 `SCORING_INITIAL`/`SCORING_FINAL` 상태를 추가하고, LLM 호출 전에 별도 커밋으로 세션을 처리 중 상태로 선점 |
| 발견 | 정상적인 예외는 `releaseInitialSubmission()`/`releaseFinalSubmission()`에서 `IN_PROGRESS` 또는 `AWAITING_FOLLOWUP`으로 되돌리지만, 서버 프로세스가 처리 중 상태 저장 직후 죽거나 release 트랜잭션 자체가 실패하면 복구 경로가 없음 |
| 영향 | 해당 세션은 `SCORING_INITIAL` 또는 `SCORING_FINAL`에 남아 이후 재시도 요청도 `INTERVIEW_SESSION_INVALID_STATUS`로 거부될 수 있음. 현재 모델에는 lease 만료 시각, 처리 시작 시각, 복구 배치가 없어 영구 고착 가능성이 있음 |
| 조치 | 이번 PR에서는 스키마 확장을 피하기 위해 즉시 release만 구현했으나, 후속 이슈에서 lease timeout 또는 처리 중 상태 자동 복구 정책을 설계해야 함 |
| PM 확인 | 2026-07-17 확인 완료. 고착 세션이 있어도 사용자는 새 면접 세션을 생성할 수 있어 사용자 피해가 제한적이고, 복구 구현 비용이 중간 이상이므로 별도 이슈로 미루는 것이 맞다고 판단 |
| 교훈 | "동시 요청 방지용 상태"는 단순 상태값만으로 끝내면 장애 복구 상태가 될 수 있다. DB에 선점 상태를 커밋하는 설계라면 만료 기준, 재시도 가능 조건, 운영 복구 절차까지 함께 정의해야 한다 |

## 12. 비커밋 개인 설정 파일(AGENTS.md)에 쌓은 팀 규칙 유실 발견

| 단계 | 내용 |
|---|---|
| 발생 | 여러 세션에 걸쳐 AGENTS.md(gitignore 대상)에 쌓아온 규칙(커밋 단위 분리, AI 실험 기록 규칙 등)이 어느 시점에 사라진 것을 발견 |
| 원인 추정 | AGENTS.md가 커밋되지 않는 개인 파일이라, 유실되어도 git 히스토리로 추적/복구가 안 됨 |
| 조치 | 팀 전체가 지켜야 할 규칙은 CLAUDE.md(커밋됨)로 이전, AGENTS.md는 순수 개인 설정만 남기도록 구조 변경 |
| 교훈 | "누가 봐도 되는 규칙"과 "나만 보는 개인 설정"을 구분해서, 전자는 반드시 커밋되는 문서에 둬야 유실 위험이 없음 |

## 13. 반복되는 AI 리뷰 지적을 판단 근거 갖고 미룬 사례

| 단계 | 내용 |
|---|---|
| 발생 | 코드래빗이 세션 고착 위험(#84 관련)에 대해 PM 확인 근거를 문서에서 확인했음에도 동일한 지적(Major, 머지 전 최소 복구 경로 필요)을 재차 제기 |
| 재검토 | PM한테 다시 확인 요청 — "이 새로운 반복 지적을 근거로 판단을 바꿀지" 재검증 |
| 판단 유지 | PM이 원래 판단(사용자 영향 제한적 + 작업 규모 중간 이상 → 별도 이슈 트래킹)을 그대로 유지하기로 확정. 대신 PR/이슈에 명확한 근거를 남겨 추적 가능하게 함 |
| 교훈 | AI 리뷰 도구가 같은 지적을 반복한다고 해서 무조건 판단을 뒤집을 필요는 없음. 다만 매번 "이 반복이 새로운 근거인지, 그냥 같은 우려의 재확인인지" 재검토는 필요함. 최종적으로는 명시적 근거를 남겨 반복 지적에도 일관되게 대응 가능하게 하는 게 핵심 |
