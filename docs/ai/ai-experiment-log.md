> 프로젝트 스페이스 가이드 "AI 기록" 요구사항 대응 문서. 최종 프롬프트뿐 아니라 시행착오 과정을 기록합니다.

## 1. 사용 모델 및 선택 이유

| 항목 | 내용 |
|---|---|
| 최종 벤더 | Claude (Anthropic) |
| 최종 모델 | Haiku 4.5 (ADR-007 확정) |

## 2. 프롬프트 설계 과정 — 시행착오 이력

### 2-0. 실제 테스트 로그 (Haiku 4.5 vs Sonnet 4.6)

| 항목 | 내용 |
|---|---|
| 테스트 방식 | Console Workbench에서 동일 Mock 답변으로 Haiku 4.5 vs Sonnet 4.6 비교 |
| 결과 | Haiku 4.5: 총점 4/25, Sonnet 4.6: 총점 2/25 — 판단 방향(부실한 답변→낮은 점수) 일치, feedback 품질도 동등 |
| 발견한 이슈 | Haiku 4.5는 응답을 마크다운 코드펜스(` ```json `)로 감싸서 반환, Sonnet 4.6은 순수 JSON — 코드펜스 스트리핑 방어 로직 필요성 발견(이슈 #8로 등록) |
| 최종 결정 | 채점 방향 일치 + 비용 효율 고려해 Haiku 4.5 채택. 코드펜스 이슈는 실 LLM 연동 시 별도 처리 |

### 2-1. 채점 기준 설계

| 단계 | 내용 |
|---|---|
| **초기안** | 3가지 단순 기준(의도이해/기술근거/트레이드오프)으로 0~25점 총점만 산정 |
| **문제 인식** | 멘토링 피드백: "채점 기준을 항목별로 상세하게 나누고, 일관성 있게 둘 것" |
| **개선 시도** | 기술적정확성(10)/핵심내용충족도(5)/근거판단과정(4)/구체성실무연계(3)/트레이드오프예외(3) = 25점, 각 항목 6단계 점수 구간표 도입 |
| **리스크 검토** | 세부항목이 5개로 늘면서 AI가 한 번에 산정할 숫자가 문항당 5개(4문항×5=20개)로 증가 → JSON 파싱 실패·숫자 누락 리스크 상승 우려 |
| **대응** | JSON 스키마 검증 + 최대 1회 재요청 + 점수 클램핑 방어로직 강화(NFR-05). 실제 Claude API로 2~3회 테스트하여 안정성 확인 후 확정 |
| **API 노출 정책** | 세부점수는 API 응답/화면에 노출하지 않고 총점(score)+종합피드백(feedback)만 제공 — 이유: (1) 프론트 UI 복잡도 증가 방지 (2) 채점 일관성 확보를 위한 내부 로직이지 사용자에게 정밀도를 보장하는 수치가 아니므로 |

### 2-2. 판정 방식 설계

| 단계 | 내용 |
|---|---|
| **검토한 대안 3가지** | ① 누적형(답변마다 채점, 누적평균 80% 이상 해금) ② 단판형(1회 판정) ③ 압박면접형(꼬리질문 3연속) |
| **비교 기준** | 구현난이도, LLM 일관성 리스크, 데모 안정성, 개발공수 |
| **판단** | 누적형은 API 호출 3배 증가+일관성 리스크 큼. 압박면접형은 3연속 판정 모두 일관되어야 해서 리스크 최고. 단판형이 4주 팀 리스크 관리에 가장 적합 |
| **최종 채택** | 단판형 + 보조 꼬리질문 1회 (질문 3개 일괄채점 → 최저점 1개에 타겟 꼬리질문 → 최종 4문항 100점 합산, 80점 이상 통과) |
| **압박면접형 처리** | 완전 폐기하지 않고 스트레치 골로 보류 (팀 정체성/차별점 유지 목적, MVP 완성 후 시간 남으면 도전) |

### 2-3. 질문 생성 방식 설계

| 단계 | 내용 |
|---|---|
| **초기 검토안** | 주제 자유 입력 방식 |
| **문제 인식** | 자유 입력 시 사전 few-shot 예시 준비 불가, 화이트리스트 무력화, 이력서와 무관한 질문 생성 위험 |
| **대안 검토** | "질문 풀에서 사전정의된 질문을 랜덤/가중 선택"하는 방식도 검토했으나 → 서비스 핵심 차별점("범용 질문은행이 아닌 이력서 기반 직접 생성")과 정면 충돌하여 기각 |
| **최종 채택** | 사용자가 6개 키워드(데이터전처리/DB/부하/보안/시스템설계/클라우드) 중 1개를 선택 → 이력서 텍스트 + 키워드를 프롬프트에 동적 주입 → AI가 매번 새로 질문 3개 + 모범답안을 생성. MVP는 검증 부담을 줄이기 위해 키워드 2개(DB, 보안)만 우선 지원 |
| **폴백 처리** | 이력서에 선택 키워드 관련 내용이 부족한 경우, "일반적인 CS 지식 관점에서 질문하라"는 지시를 프롬프트에 포함 |

### 2-3-1. 키워드 반영 경로 확인 (Real LLM vs Mock)

| 항목 | 내용 |
|---|---|
| 확인 배경 | IS-002 설계 논의 중 레이(실무 매니저)가 "질문 키워드가 실제로 반영되는지" 질문 |
| 확인 결과 | Real LLM 경로는 keyword가 요청 → 서비스 → 프롬프트 → 템플릿까지 정확히 반영됨(테스트 검증 완료). MockLlmClient는 keyword와 무관하게 고정 질문 반환 |
| 확인 | 의도된 설계 — Mock은 코드 흐름 검증용이며, 키워드별 내용 차이는 필요 없음. 그대로 유지 |

### 2-4. 페르소나(톤) 설계

| 단계 | 내용 |
|---|---|
| **초기 아이디어** | 기술 성향(스타트업 vs 대기업) 기반 페르소나 — 이후 "톤(널널함/깐깐함)"과 "주제 키워드"로 관심사가 분리되며, 최종적으로는 톤(2종)+키워드(2종) 2개 축으로 정리 |
| **구현 방식** | System Prompt 교체로 구현 (개발 비용 ≈ 0). 실제 대사 문구는 DB가 아닌 파일로 분리 관리(`lenient.txt`, `strict.txt`) — 톤 조정 시 DB 마이그레이션 불필요 |
| **원칙** | 페르소나 수 절대 상한 3개, 기본 2개(널널한 대리/깐깐한 과장)로 MVP 확정 |

### 2-5. 모범답안 생성 시점 조정 및 저장 구조 검증

| 단계 | 내용 |
|---|---|
| **초기 설계 오류** | 요구사항 초안에 "채점 호출 내에서 모범답안 생성, 저장 안 함(휘발성)"으로 기재 |
| **실제 필요 발견** | 채점 로직 개발 중 "모범답안을 서버에 저장해서 채점 시 재사용해야 한다"는 요구사항 확인 (질문생성 LLM과 채점 LLM 호출이 분리되어 있어 저장 필요) |
| **호출 횟수 검증** | 모범답안을 "질문 생성 호출 내에서 함께 생성"하면 질문 생성 영역의 추가 호출을 막을 수 있음을 확인 후 진행. 이후 #59에서 꼬리질문 생성 전용 호출을 추가해 현재 정상 호출 횟수는 세션당 4회로 확정 |
| **최초 저장 구조 확정** | `session_id` 기반 복합키(`session_id`+`question_id`)로 `question_text`까지 함께 저장하는 구조로 확정, 이후 코드리뷰(코덱스) 반영해서 FK/UNIQUE 제약까지 보강(PR #28) |
| **최종 저장 구조 결정** | 이건희와의 재확인 결과, 질문 텍스트 중복 저장을 피하기 위해 `message_id`(FK)로 기존 `messages` 테이블을 참조하는 구조가 맞다고 확정 → `questions` 테이블을 `message_id` 단일 PK/FK + `expected_answer`로 재설계 |
| **문서 반영** | FR-03(생성 시점 저장), FR-04(조회 후 채점), ERD, api-spec(IS-002), open-questions.md #9 정정 완료 |

### 2-6. 채점 계약 정합화 (최초/최종 문항 수 불일치 발견 및 수정)

| 단계 | 내용 |
|---|---|
| 발견 | `judgment` 도메인(③, PR #18)이 이미 "최종 4문항 전체 재채점"을 전제로 설계되어 있었으나, `global.llm`(②) 쪽 실제 요청/응답 계약은 "꼬리질문 1개만 채점하고 turn 번호만 유지"하는 3문항 구조로 남아있음을 발견 |
| 원인 확인 | 기획서 §3 원문("4문항 합산 100점 만점")을 재확인해 "최저점 문항을 대체"가 아니라 "4문항 전체를 유지하며 보강"하는 게 맞는 설계임을 확정 |
| 수정 | `EvaluationRequest`를 3문항(turn 번호만)에서 4문항 전체(질문+답변+모범답안 포함)로 재설계. 이 과정에서 코드리뷰로 turn 중복/범위/누락/weakestQuestionId 처리 등 10라운드 이상의 세부 검증을 거침(ADR-010) |

> 개발 과정에서 발생한 SSOT 검증, 코드리뷰 반영 방어, 도메인 경계와 호출 원칙 충돌 기록은
> [`harness-troubleshooting.md`](harness-troubleshooting.md)로 분리했다.

### 2-10. LLM 재요청 상한 축소 (최대 1회)

| 단계 | 내용 |
|---|---|
| 발생/발견 | LLM 응답 스키마 검증 실패 시 `LlmInvocationService`가 재시도를 과하게 허용하고 있어, 호출 경로별 최악 케이스 호출 수가 예산 대비 커질 수 있음을 확인 |
| 원인/근거 확인 | `LlmInvocationService`의 질문 생성, 최초 채점, 꼬리질문 생성, 최종 채점 `@Retryable` 경로와 관련 재시도 테스트를 확인했고, 운영 문서(`llm-cost-policy.md`, `failure-policy.md`)의 재요청 상한 문구도 같은 정책을 설명하고 있음을 확인 |
| 조치/결정 | `maxAttempts=2`로 줄여 최초 1회 + 재시도 1회만 허용하도록 변경했다. #59 구현 후 현재 코드 기준 정상 호출은 4회, 최악 케이스 호출 횟수는 8회다. 테스트 기대값도 새 재시도 정책에 맞춰 갱신했다 |

### 2-11. 꼬리질문 생성 프롬프트 신규 설계

| 단계 | 내용 |
|---|---|
| 발생/발견 | #59 구현으로 최초채점에서 반환된 최저점 문항을 바탕으로 꼬리질문 1개와 최종 채점용 모범답안을 별도 생성해야 함 |
| 원인/근거 확인 | `evaluateFinalAnswers`는 turn 1~4 전체 재채점을 기대하지만, 기존 구현에는 turn 4 질문과 모범답안을 만드는 LLM 호출이 없었다. 이슈 #59 작업지시서의 입력 계약(`weakestQuestionId`, 원래 질문, 사용자 답변, feedback)과 저장 계약(`messages.role=QUESTION, turn=4`, `questions.message_id + expected_answer`)을 기준으로 확인 |
| 조치/결정 | 기존 질문 생성 프롬프트의 페르소나 system prompt 재사용 구조를 유지하고, user prompt는 원래 질문·부실 답변·feedback에서 빠진 부분을 겨냥하도록 별도 템플릿(`prompts/question-generation/follow-up-user.txt`)으로 작성했다. few-shot 2개를 자체 작성해 포함하고, 출력은 `{ followUpQuestion, expectedAnswer }` 순수 JSON으로 제한했다 |

### 2-11. 최종 채점 범위 재확정 (turn 4 단독 채점)

| 단계 | 내용 |
|---|---|
| 발생/발견 | 최초 1~3을 최종 LLM에서 다시 채점하면 이미 확정한 점수가 비결정적으로 바뀌고, 최종 호출에서 20개 루브릭 숫자를 다시 생성해야 하는 문제가 확인됐다 |
| 조치/결정 | 최종 LLM의 신규 채점 대상은 turn 4 한 건으로 제한한다. 최초 1~3은 서버 확정 점수를 보존하고, 질문·답변·확정 점수·피드백만 종합 피드백용 읽기 전용 컨텍스트로 전달한다(이슈 #60, ADR-014) |
| 최종 합산 | 서버가 `기존 turn 1~3 확정 점수 + clamp(turn 4)`로 0~100 총점과 80점 이상 합격 여부를 재계산한다. 외부 최종 응답에는 turn 1~4 점수를 모두 포함한다 |

### 2-12. IS-002 답변 제출/채점 API 부재 발견

| 항목 | 내용 |
|---|---|
| 발견 배경 | 레이(실무 매니저)가 4단계 LLM 호출 전체 흐름(질문생성 → 최초채점 → 꼬리질문생성 → 최종채점)이 다 이어지는지 확인 요청, 이 과정에서 발견 |
| 발견 내용 | 질문 생성(IS-001)은 API로 구현되어 있으나, 답변 제출/채점(IS-002) 엔드포인트 자체가 없음. ②가 채점 LLM을 직접 호출하고 있으나, ③(JudgmentScoringService)로 연결하는 정식 흐름이 없었음 |
| 조치 | 이슈 #73/#78로 ②/③ 경계 정리 먼저 진행, IS-002 엔드포인트는 ③(최용성) 설계 후 ②(김한비)가 컨트롤러 구현하는 순서로 진행 예정 |

### 2-13. End-to-end 실측 검증 (IS-001~IS-002 전체 흐름)

| 항목 | 내용 |
|---|---|
| 검증 범위 | 질문생성(a) → 최초채점(b) → 꼬리질문생성(c) → 최종채점(d) 전체 흐름을 실제 Claude API로 끝까지 실행 |
| 호출 횟수 | 4회 (질문생성1, 최초채점1, 꼬리질문생성1, 최종채점1) — 설계대로 정확히 일치 |
| JSON 파싱 안정성 | 전 단계 파싱 성공, 5개 루브릭 필드 검증 통과 |
| 소요 시간 | 약 49.4초 (세션 하나 전체) |
| 상태 전이 | IN_PROGRESS → AWAITING_FOLLOWUP → COMPLETED 정확히 확인 |
| 발견 | 초기 테스트 기대값(최종 응답=turn4 단독)이 실제 API 계약과 달라 1차 실패, 재확인 후 보정하여 재검증 성공 |

### 2-14. raw weakestQuestionId 직접 사용 문제 및 재설계

| 항목 | 내용 |
|---|---|
| 발견 | InterviewService가 최저점 문항(꼬리질문 대상)을 정할 때, ③(judgment)의 보정을 거치지 않고 LLM raw weakestQuestionId를 그대로 사용하고 있었음 |
| 확인 | 최용성 확인 — 비정상 응답 시 raw값과 보정값의 최저점 순위가 달라질 수 있음 |
| 재설계 | ②가 raw evaluations를 ③에 넘기면 → ③이 보정 → 보정된 weakestQuestionId를 ②가 꼬리질문 흐름에 사용 |

### 2-15. 외부 API questionId 식별자 통일 (turn 기준)

| 항목 | 내용 |
|---|---|
| 배경 | 코드래빗이 처음엔 "questionId를 Message.id 기준으로 통일하라"고 지적해 반영했으나, 최용성이 채점 파이프라인 코드를 확인한 결과 turn(1~4) 기준이 더 적합하다고 재확인 |
| 결정 | 외부 API의 questionId는 turn(1~4)으로 통일. 내부적으로는 questions.message_id/Message.id를 통한 매핑을 그대로 유지 |
| 근거 | 채점 로직 전체가 이미 turn 기준으로 설계되어 있어, turn 통일이 변환 로직/버그 위험을 줄임 |

### 2-16. 저장 구조와 API 표기 분리 확정

| 항목 | 내용 |
|---|---|
| 확인 배경 | PM이 "questionId를 turn 기준으로 통일한 것이 questions 테이블 저장 구조(message_id PK/FK) 자체를 바꾼 것인지" 확인 요청 |
| 결론 | 저장 구조(message_id PK/FK)는 그대로 유지. 바뀐 건 API 요청/응답에 노출되는 questionId 값뿐, 내부 매핑(turn→Message 조회→message_id) 로직은 유지됨 |

### 2-17. 최종 채점 응답의 turn 1~4가 서버 병합 결과임을 실측 확인

| 항목 | 내용 |
|---|---|
| 확인 배경 | E2E 검증(2-13) 중 최종 응답에 turn 1~4가 전부 포함된 것을 보고, LLM이 4개를 재채점한 것인지 서버가 합친 것인지 확인 필요 |
| 확인 결과 | LLM은 turn 4만 채점(코드 레벨로 강제, 프롬프트에도 "Score only turn 4" 명시). 서버가 저장된 최초 1~3 점수와 LLM의 turn 4 결과를 합쳐서 외부 API로 응답 |
| 근거 | LlmInvocationService가 최종 요청에 turn 1~3이 섞이면 호출 전에 실패시킴, JudgmentScoringService가 최초 점수 normalize+turn4 합산 |

## 3. 최종 적용 방식 요약

- **모델**: Claude Haiku 4.5, 현재 코드 기준 세션당 AI 호출 4회
- **질문 생성**: 이력서+키워드(1개) 동적 주입, 3문항 + 모범답안 동시 생성
- **채점**: 5개 세부항목(내부) → 총점 100점 만점 산출, API/화면엔 총점+피드백만 노출
- **꼬리질문**: 3문항 중 최저점 1개에 한정, turn 4만 신규 채점하고 최초 1~3 확정 점수와 합산해 80점 이상 통과
- **방어로직**: JSON 스키마 검증, 최대 1회 재요청, 점수 클램핑
