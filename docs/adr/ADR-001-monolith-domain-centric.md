# ADR-001 — 모놀리식 + 도메인 중심 아키텍처 채택

- 상태: 승인 (기획서 v5.1, 16장 "기술적 의사결정 근거")
- 결정자: 팀 전원 (기획서 최종 마감 2026-07-08 이후 동결)
- 근거 문서: `[기획서] 커리어 던전 v5.1.pdf` 6장(팀 구조), 9장(시스템 아키텍처), 16장(ADR)

## 배경

4명 전원이 백엔드를 담당하고, 표지민 1명이 인증·인프라·프론트·공통코드까지 겸임하는
구조로 3주 실개발을 진행한다. 여러 서비스로 쪼개면 배포/통신/트랜잭션 경계 설계에
드는 초기 비용이 3주 안에서는 감당하기 어렵다.

## 결정

**모놀리식 + 도메인 중심 패키지 분리**를 채택한다. 물리적으로는 단일 Spring Boot
애플리케이션이지만, 논리적으로는 6개 도메인(① 파일 파이프라인 ② 면접 엔진+LLM
③ 평가·게이지·해금 ④ 인증 ⑤ 인프라 ⑥ 프론트)으로 나눠 담당자별 경계를 명확히 한다.

- 코드 구조: `domain.resume`, `domain.interview`, `domain.message`, `domain.persona`,
  `domain.judgment`, `domain.progress`, `domain.auth`, `global.*` (실제 패키지는
  `docs/ai/README.md`의 "경로 → 오너" 표 기준).
- 도메인 경계는 **입출력 계약**으로 강제한다: ②의 책임은 "LLM이 평가 원시값을 반환하는
  시점"까지, ③의 책임은 "그 원시값에 루브릭을 적용하는 시점"부터. 이 경계를 기준으로
  두 도메인은 서로 Mock 데이터로 독립 개발할 수 있다 (기획서 6장).
- 공통 코드(예외 처리, 응답 포맷)의 오너는 ④번(표지민)으로 확정한다 (CM-002).

## 핵심 근거

- MSA는 이 프로젝트 규모에서 과설계이며, 모놀리식으로 빠르게 완성한 뒤 필요하면
  확장 가능한 구조를 유지하는 것이 3주 실개발 기간 안에서 현실적이다.
- 도메인 경계를 코드 구조(패키지)로 강제하면, 물리적으로 분리하지 않고도 담당자별
  책임 소재가 명확해진다 — `docs/ai/owners/*.md`의 "손대지 말 것" 절이 이 경계를
  코드 리뷰 단계에서 다시 강제한다.

## 대안 및 반려

- **MSA(도메인별 서비스 분리)** — 반려. 서비스 간 통신, 배포 파이프라인, 분산 트랜잭션
  설계에 드는 초기 비용이 3주 일정에서 감당 불가능하다고 판단.
- **완전한 계층형(레이어드) 구조, 도메인 미분리** — 반려. 4명이 동시에 작업할 때
  담당 경계가 불명확해져 충돌·중복 작업 위험이 커진다.

## 결과 (기대)

- 배포는 단일 아티팩트로 단순화되고, 도메인 경계는 패키지 구조 + 하네스 규칙
  (`docs/ai/README.md` 경로 라우팅, owner 파일의 "손대지 말 것")으로 관리된다.
- ②/③ 경계에서 Mock 데이터 기반 독립 개발이 가능해져, LLM 실연동 지연이 ③ 작업을
  블로킹하지 않는다 (`docs/requirements/wbs.md`의 "인터페이스 추상화 1순위" 참고).
