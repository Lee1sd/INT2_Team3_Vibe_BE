# ADR-014 — 최종 LLM은 turn 4만 채점하고 최초 1~3 서버 확정 점수와 합산

- 상태: 제안
- 작성자: 최용성
- 작성일: 2026-07-15
- 관련 이슈/PR: #60, #59, #81, PR #62, PR #82, ADR-008, ADR-009, ADR-011, ADR-013

## 배경

기존 최종 채점 계약은 최초 turn 1~3과 꼬리질문 turn 4를 LLM에 모두 보내 네 문항을
다시 채점했다. 이 방식은 최초 채점에서 이미 서버가 확정한 점수가 최종 호출에서 달라질 수
있고, 네 문항의 20개 루브릭 숫자를 다시 생성해 비용과 스키마 이탈 가능성을 늘린다.

꼬리질문은 최초 최저점 문항을 보강하기 위한 별도 문항이므로, 최초 1~3의 확정 점수는
유지하고 사용자가 새로 제출한 turn 4만 채점하는 계약이 필요하다.

## 결정

- 최초 채점은 turn 1~3을 평가하고 서버가 루브릭 clamp 후 확정 점수를 보존한다.
- 최종 LLM 요청에서 채점 대상은 turn 4의 질문·사용자 답변·예상답변 한 건으로 제한한다.
- 최초 1~3의 질문·사용자 답변·서버 확정 점수·개별 피드백은 `previousEvaluations`라는
  별도 읽기 전용 컨텍스트로 전달한다. 이는 면접 전체의 강약점과 꼬리질문 보완 정도를
  종합 피드백에 연결하기 위한 정보이며, 1~3 재채점이나 turn 4 점수 산정에 사용하지 않는다.
- 최종 LLM 응답의 `evaluations`는 turn 4 한 건이어야 하며 feedback과 5개 루브릭을
  모두 포함해야 한다.
- 서버는 보존된 최초 1~3 점수와 clamp한 turn 4 점수를 합쳐 최종 0~100 점수와
  80점 이상 합격 여부를 계산한다. LLM이 보고한 `totalScore`와 `passed`는 신뢰하지 않는다.
- 외부 IS-002b 응답은 기존과 같이 questionId 1~4의 점수, 최종 총점, 합격 여부,
  `overallFeedback`을 반환한다. 1~3은 기존 확정값이고 4만 신규 평가값이다.
- 꼬리질문은 `messages(role=QUESTION, turn=4)`로 저장하고, 예상답변은 해당
  `Message.id`를 PK/FK로 하는 `questions(message_id, expected_answer)`에 저장한다.
- 위 두 저장이 성공한 직후 같은 트랜잭션에서 세션을 `AWAITING_FOLLOWUP`으로 바꾼다.
  turn 4 답변 채점과 최종 판정 저장 성공 후에만 `COMPLETED`로 바꾼다.
- 답변 제출은 `준비 트랜잭션 → LLM 호출(트랜잭션 밖) → 반영 트랜잭션`으로 나눈다.
  준비 단계와 반영 단계에서 세션을 다시 잠그고 상태·소유자·기존 결과를 검증한다. 이로써
  외부 호출 대기 중 DB 커넥션과 비관적 잠금을 점유하지 않으면서 반영 시점의 정합성을 지킨다.
- 단일 애플리케이션 인스턴스에서는 세션 단위 JVM 잠금으로 같은 세션의 중복 LLM 호출을
  직렬화한다. 다중 인스턴스 경쟁은 반영 트랜잭션의 재검증과 DB UNIQUE로 데이터 중복을
  차단하되, 외부 호출 자체는 중복될 수 있다.

## 핵심 근거

- 최초 확정 점수가 후속 LLM의 비결정성으로 바뀌지 않는다.
- 종합 피드백은 최초 최저점 답변과 꼬리질문 보완 정도를 함께 설명할 수 있다.
- 최종 요청 루브릭 숫자가 20개에서 5개로 줄어 JSON 누락과 범위 이탈 표면이 작아진다.
- 최종 총점과 합격 여부를 서버가 재계산하는 기존 신뢰 경계를 유지한다.
- 외부 API의 4문항·100점 계약은 유지하므로 프론트 응답 구조를 바꾸지 않는다.

## 대안 및 반려

- **turn 1~4 전체 재채점** — 전체 문맥을 한 번에 평가할 수 있지만 최초 확정 점수가
  달라지고 비용·스키마 위험이 커져 반려했다.
- **1~4를 모두 동일한 채점 항목으로 보내고 turn 4 점수만 소비** — 종합 피드백 문맥은
  풍부하지만 요청 계약과 실제 소비 범위가 달라 불필요한 재평가를 유도하므로 반려했다.
- **turn 4만 전달하고 서버에서 피드백 문자열을 이어 붙임** — 점수 계약은 단순하지만
  최초 답변과 보완 답변의 의미 연결을 LLM이 볼 수 없어 종합 피드백 품질이 낮아져 반려했다.
- **`PROCESSING_*` 상태를 저장하고 LLM 호출** — 다중 인스턴스의 중복 호출도 막을 수 있지만,
  프로세스 중단 시 상태가 영구 고착되지 않도록 TTL·소유 토큰·복구 작업·상태 DDL이 함께
  필요하다. 현재 단일 모놀리스 MVP 범위를 넘어가므로 반려했다.

## 결과

- `global.llm`의 최종 요청·응답 검증은 turn 4 한 건을 강제한다.
- 최종 요청은 turn 1~3의 읽기 전용 컨텍스트 3건과 점수 범위(0~25), 필수 텍스트를
  검증해 피드백 근거 누락과 스키마 이탈을 조기에 거부한다.
- `domain.judgment`의 최종 채점은 최초 확정 결과와 turn 4 원시 응답을 함께 받아 합산한다.
- 최초 확정 turn 1~3의 점수와 개별 피드백은 `answer_scores`에 `(sessionId, turn)` 단위로
  보존해 다음 요청에서 `previousEvaluations`를 복원한다.
- 최초 점수 영속화와 turn 4 질문·예상답변 조회, 세션 상태 전이는 #59와 #81 답변 제출
  오케스트레이션에서 이 계약에 맞춰 연결한다.
- 최종 `passed`는 서버가 계산한 `totalScore >= 80`에서만 파생하며, 애플리케이션 모델과
  DB CHECK가 서로 다른 합격 상태의 저장을 모두 거부한다.
