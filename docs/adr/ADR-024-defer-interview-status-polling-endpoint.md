# ADR-024 — 면접 처리 상태 전용 폴링 API 도입 연기 (MVP)

- 상태: 제안
- 작성자: 표지민
- 작성일: 2026-07-27
- 관련 이슈/PR: ADR-004, `docs/requirements/wbs.md` ⑤, 이슈 #85

## 배경

`docs/requirements/wbs.md` ⑤ 인프라 섹션에는 "비동기 폴링 구조 — 면접 처리 상태 폴링
엔드포인트 설계"가 중요도 "중"으로 남아 있다. ADR-004는 이력서 파싱 상태(`RS-002`)와
면접 처리 상태 모두 폴링으로 조회하기로 확정했지만, 실제로는 이력서 쪽만 전용 GET
폴링 API(`RS-002`)로 구현됐고, 면접 쪽은 `IS-002`(`POST /api/interviews/{id}/answers`)가
LLM 채점이 끝날 때까지 응답을 들고 있는 동기 long-request로 동작한다 — 프론트는 이
POST 응답을 기다리는 동안 `isSubmitting` 같은 로컬 상태로 로딩 UI만 표시한다.

또한 이슈 #85는 `SCORING_INITIAL`/`SCORING_FINAL` 처리 중 상태가 서버 다운이나 release
실패로 고착될 가능성을 지적하면서, lease timeout/자동 복구 도입 여부를 열어뒀다. 이
문제가 실사용에서 재현되거나, 중간 상태를 사용자에게 보여줘야 하는 UX 요구가 생기면
"처리 상태를 어떻게 조회하게 할 것인가"라는 질문이 다시 떠오른다. 지금 시점에 이걸
결정하지 않고 넘어가면, 나중에 "그때 왜 전용 API를 안 만들었지?"를 다시 논의하게 된다.

## 결정

**MVP 기간에는 면접 처리 상태 조회 전용 GET 폴링 API를 새로 만들지 않는다.**

- `IS-002`는 지금처럼 동기 long-request(FE가 POST 응답을 기다리며 `isSubmitting` 같은
  로컬 로딩 상태만 표시)를 유지한다.
- 이력서 `RS-002` 폴링은 그대로 유지한다 — ADR-004의 결정과 충돌하지 않는다. 이번
  결정은 면접 처리 상태에 한정된다.
- 이 ADR은 "지금은 도입하지 않는다"는 연기 결정만 기록한다. 이번 PR에서는 문서만
  변경하며, 관련 코드·API를 구현하지 않는다.

## 핵심 근거

- 3주 MVP 일정에서 아직 실제로 겪지 않은 문제(처리 중 상태 고착, 중간 상태 UX 필요)를
  선제적으로 풀기 위해 새 엔드포인트·FE 폴링 로직을 추가하는 비용을 지금 들일 이유가
  없다. `IS-002`의 동기 long-request는 이미 동작하고 있고, LLM 응답 지연(3~10초) 수준은
  현재 방식으로 커버 가능하다(ADR-004 핵심 근거와 동일 판단).
- 이슈 #85가 우려하는 처리 중 상태 고착은 "서버 다운/release 실패"라는 드문 상황에서만
  발생하고, 이슈 본문에도 우선순위가 "낮음"으로 명시되어 있다 — 아직 실사용에서
  재현된 적이 없다.

## 대안 및 반려

- **지금 전용 상태 조회 API(`GET /api/interviews/{id}/status` 등)를 미리 만들어둔다** —
  반려. 아직 필요성이 실증되지 않은 기능을 먼저 설계하면, 이슈 #85의 lease/복구 정책이
  나중에 확정될 때 상태값·응답 계약을 다시 바꿔야 할 가능성이 높다(예: 고착 복구 시
  되돌아갈 상태가 `IN_PROGRESS`/`AWAITING_FOLLOWUP` 중 무엇인지도 아직 미정). 확정 안 된
  정책 위에 API 계약부터 얹으면 이중 작업이 된다.
- **`IS-002`를 지금 비동기 방식(즉시 202 응답 + 별도 폴링)으로 바꾼다** — 반려. FE의
  `isSubmitting` 기반 동기 대기 UX를 이미 구현해 쓰고 있어, 지금 바꾸면 FE 작업이
  추가로 필요하다. 바꿔야 할 만큼 급한 문제(게이트웨이/브라우저 타임아웃, 실사용
  고착 재현)가 아직 관측되지 않았다.

## 결과 (기대)

- MVP 기간에는 `IS-002` 동기 long-request, `RS-002` 폴링 구조를 그대로 유지한다.
- 아래 조건 중 하나라도 실제로 발생하면 이 결정을 재검토한다:
  - 게이트웨이/브라우저 타임아웃으로 `IS-002`의 POST 연결이 끊기는 사례가 발생
  - 이슈 #85의 `SCORING_INITIAL`/`SCORING_FINAL` 고착이 실사용에서 재현됨
  - 프론트에서 "처리 중" 중간 상태를 화면에 보여줘야 하는 UX 요구가 생김
- 재검토가 필요해지면, ADR-004가 이미 확정한 폴링 방식(SSE 아님)을 그대로 따라 면접
  처리 상태 전용 GET 상태 API + FE 폴링을 도입한다. 이번 ADR은 "지금 당장은 안 한다"는
  연기 결정만 남기고, 실제 도입 시점의 설계(상태값, lease 처리 등)는 그때 별도 ADR/이슈로
  구체화한다.
- 2026-07-27 팀 합의로 위 방향(MVP는 POST+스피너 유지, GET 폴링 미도입, #85 처리 시점에
  재검토)을 확정했다. 재시도 최악 시간도 **목(Mock) 기반으로 재현**해봤다(실 Claude 강제
  실패 아님) — 호출당 300ms 지연 + 1차 스키마 실패 → 2차 정상 응답, `@Backoff(delay=500ms)`
  포함 측정 시 `evaluateInitialAnswers` 1143ms, `generateFollowUp` 1339ms로 대략
  정상×2+backoff 수준이었다. 실사용 체감은 이 재시도 오버헤드보다 기존 정상 응답 시간
  (13~17초)의 영향이 더 크며, 실제로 30초 이상 체감되면 그때 폴링/API 분리를 재논의한다.
