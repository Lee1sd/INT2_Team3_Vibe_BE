## 서비스 개요

- 한줄 소개: 이력서를 업로드하면 페르소나가 다른 AI 면접관이 질문을 던지고, 신뢰도
  게이지를 채워 상위 면접관을 해금하는 게임형 개발자 면접 연습 서비스.
- 서비스명 후보: 커리어 던전
- 팀 구성: 4명 전원 백엔드 담당 (표지민: 백엔드 도메인 + 프론트 화면 제작 겸임 / API
  연동은 각 도메인 담당자가 직접)
- 아키텍처: 모놀리식 + 도메인 중심 개발 (`docs/adr/ADR-001-monolith-domain-centric.md`)
- 웹 브라우저 기반, 반응형 디자인으로 모바일 브라우저 접근 지원(네이티브 앱 아님).

## 1. 기획 의도 및 배경

기존 AI 모의면접 서비스는 질문 → 답변 → 피드백의 단발성 구조로, 반복 동기가 약하다.
이 서비스는 미연시(비주얼노벨)의 공략·해금 구조를 커리어 시뮬레이션으로 재해석해,
문서 기반 꼬리질문 + 해금 게임 구조로 "반복해서 돌아오는" 면접 연습을 만든다.

| 차별점 | 내용 |
| --- | --- |
| 문서 기반 맞춤 질문 | 범용 질문 은행이 아닌, 업로드된 이력서/포트폴리오에서 직접 질문 생성 |
| 꼬리질문 | 단판형 + 보조 꼬리질문 1회. 직전 답변의 허점을 파고드는 멀티턴 압박감 재현 |
| 페르소나 해금 | 면접관마다 스타일·톤이 다르고, 게이지를 채워야 다음 면접관 공략 가능 |
| 성장 서사 | "사수의 신뢰를 얻어 성장하는 주니어"라는 커리어 시뮬레이션 서사 |

**제외 확정**: 코드 디펜스 / 음성 답변 / AI 파인튜닝(MVP 범위, 스트레치골의 "데이터
플라이휠"로만 이관).

## 2. 타겟 사용자

- 핵심 타겟: 취업 준비 중인 주니어 백엔드 개발자(신입~1년차)
- 페인 포인트: 실전 면접 경험 부족 / 본인 포트폴리오 기반 꼬리질문을 스스로 뽑기 어려움
  / 모의면접 스터디의 진입장벽
- 사용 시나리오: 지원 직전 이력서 업로드 → 예상 꼬리질문 방어 연습 → 반복 플레이로
  답변 완성도 향상

## 4. 페르소나 & 면접 스타일 & 해금 시스템 설계 원칙

공통 규칙(모든 페르소나 동일): 3개 답변 일괄채점 → 최저점 답변 1개에 타겟 꼬리질문
1회(무조건 발생) → 4문항 합산 최종판정.

| 값 | 설명 |
| --- | --- |
| 톤 | 널널함/깐깐함 — System Prompt 교체로 구현(개발 비용 ≈ 0) |
| 키워드 | 데이터전처리/DB/부하/보안/시스템설계/클라우드(MVP는 2~3개만 노출 권장) — 사용자 선택 키워드(1개)를 프롬프트에 동적 주입 |

설계 원칙(구현 시 반드시 지킬 제약):

- **설정 기반 설계**: 페르소나 정의를 코드 수정 없이 확장할 수 있도록 설정 파일(Config)
  중심의 아키텍처를 채택한다(NFR-07 스타일 엔진 추상화와 동일한 원칙).
- **페르소나 수 원칙**: 기본 2개 · **절대 상한 3개** · 4개 이상은 논의 금지. Lv.3(압박
  페르소나)까지가 이 프로젝트의 최대 범위이며, 그 이상을 요구하는 논의가 나오면 스코프
  아웃 대상임을 먼저 알린다.
- **컷라인**: 일정 지연 시 레벨2(과장) 컷 → 레벨1(대리)만으로 데모 성립.

## 5. 레벨별 뱃지 변천사 디자인

4단계 성장형 보상 구조. 레벨이 오를수록 더 완성된 모습의 "머쓱이" 뱃지가 부여된다.

| Stage | 트리거 | 컨셉 |
| --- | --- | --- |
| Stage 1 | 가입 직후 | 엉성한 기본 윤곽 + "프로그램 머쓱..." 레터링의 초안 형태 |
| Stage 2 | Lv.1(널널한 대리) 해금 | 선이 정돈되고 컬러가 입혀진 기본 완성형 |
| Stage 3 | Lv.2(깐깐한 과장) 해금 | 코드 블록을 다루며 "디버깅!"을 외치는 실전 적용형 |
| Stage 4 | Lv.3(압박 페르소나) 해금 | 부끄러운 듯 머리를 긁적이는 마스터 성취형 (MVP 범위에서는 실제 지급 불가) |

⚠️ `docs/api/api-spec.md`의 `BG-001` 비고와 `docs/state/invariants-and-state-machines.md`
§5에 이 4단계 매핑에 대한 "팀 확인 필요" 항목이 있습니다.

## 6. 팀 구조 및 개발 방식

도메인 6분할과 입출력 경계(요약, 상세는 `docs/ai/README.md`/`docs/ai/owners/*.md`가 SSOT):

| 도메인 | 주요 작업 | 입출력 경계 |
| --- | --- | --- |
| ① 파일 파이프라인 | Multipart 검증, S3 임시 업로드, PDFBox 추출, 원본 즉시 삭제, 텍스트 캐싱 | 출력: 추출 텍스트 → ② |
| ② 면접 엔진 + LLM | LLM 클라이언트 인터페이스+Mock, 페르소나 스타일 엔진, 프롬프트 조립, JSON 스키마 검증·재시도 | 출력: 평가 JSON + attempt 상태 → ③ |
| ③ 평가·게이지·해금 | 평가 JSON → 점수 변환, 히스토리 윈도잉, 게이지 환산, 해금 조건 판정, Progress API | 출력: 게이지·해금 상태 → 프론트 |
| ④ 인증(Auth) | Google OAuth2, Spring Security, JWT 발급·재발급, 도메인별 접근 제어 | 전 도메인 인증 기반 제공 |
| ⑤ 인프라 | Docker/GitHub Actions CI/CD, 면접 처리 상태 폴링 | - |
| ⑥ 프론트엔드 | 필수 5화면, API 연동, 게이지/해금 상태 시각화 | - |

- **② 도메인의 책임 끝**: LLM이 평가 원시값을 반환하는 시점.
- **③ 도메인의 책임 시작**: 반환된 평가값을 루브릭에 적용하는 시점. 이 경계를 기준으로
  두 도메인은 Mock 데이터로 독립 개발 가능하다.
- **공통 코드 오너**: ④번(표지민) 확정 — 예외 처리, 공통 응답 포맷 등 전 도메인 공통
  규칙 관리(CM-002).

## 7~9. 기술적 도전 과제 / 기술 스택 / 시스템 아키텍처

9개 기술적 도전 과제는 `docs/requirements/functional-requirements.md`의 NFR-01~NFR-09에
1:1로 대응합니다(이 문서에서 중복 서술하지 않음). 기술 스택 요약:

| 구분 | 스택 및 선택 이유 |
| --- | --- |
| Framework | Spring Boot + JPA |
| Database | MySQL |
| Storage | AWS S3 |
| Library | Apache PDFBox |
| LLM | Claude(Haiku 4.5/Sonnet 4.6) — `docs/adr/ADR-003-llm-vendor-selection.md` |
| Frontend | React + TypeScript + Tailwind CSS |
| Auth | OAuth2(Google) + Spring Security + JWT — `docs/adr/ADR-006-google-oauth2-over-self-auth.md` |

시스템 아키텍처(개념도, 기획서 9장 원문):

```
[React SPA] --REST(multipart/JSON)--> [Spring Boot 모놀리식 API]
  ├─ ④ 인증(Auth) / ⑤ 인프라: Google OAuth2 / 비동기 폴링 공통 / 배포
  ├─ ① 파일: 검증 → [S3] 원본 → PDFBox → [MySQL] extracted_text
  ├─ ② 엔진: 스타일 로드 → 프롬프트 조립 → [LLM Interface] → 실구현 or Mock
  └─ ③ 평가: JSON 파싱 → 루브릭 → 단발 판정값 → 해금
       └─ Message 테이블 (멀티턴 윈도잉) → ②로 재공급
```

## 13. 기대 효과

- 사용자: 본인 문서 기반 실전형 꼬리질문 연습 + 게임적 반복 동기.
- 팀: 프롬프트 튜닝 및 QA 부담을 낮춰 4주 내 완결성 보장. 페르소나/레벨 추가가 용이한
  확장성 있는 구조를 증명.
