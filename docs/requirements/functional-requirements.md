## 기능 요구사항 (Functional)

### FR-01 — 이력서/포트폴리오 업로드·추출

- **상세 설명**: 이력서(필수, 최소 1개~최대 3개)/포트폴리오(선택, 최대 3개)를 업로드받아 텍스트 추출 및 캐싱한다.
  (✅ 2026-07-10 확정 — 마이페이지 와이어프레임(`06-mypage.svg`) 기준. `docs/requirements/open-questions.md` #1 참고)
- **입력**: multipart 파일 (최대 10MB), `type`(RESUME/PORTFOLIO)
- **처리 로직**:
  1. 확장자 화이트리스트 + 매직넘버 검증
  2. type별 개수 검증 (RESUME 1개 이상 필수 + 최대 3개, PORTFOLIO 0~3개)
  3. 동일 type 재업로드 시 기존 레코드 교체(UPSERT)
  4. S3 임시 버킷 업로드
  5. PDFBox 텍스트 추출
  6. PII 마스킹 처리
  7. 원본 즉시 삭제(try-finally)
  8. `extracted_text`(마스킹됨), `parse_status` DB 저장
- **출력/결과**: `resumeId`, `type`, `parseStatus`
- **예외처리**: 확장자·용량 위반 400 / RESUME 미존재 상태로 세션 생성 시도 시 차단 / PDFBox 추출 실패 시 `parse_status=FAILED` 저장 후 재업로드 안내 / 업로드 후 30일 경과 시 삭제
- **관련 API**: `RS-001`, `RS-002`
- **기획서 근거**: 3장#1 확정(이력서/포트폴리오 각 1개)
- **오너**: 이건희 (`docs/ai/owners/lee-geonhui.md`)

### FR-02 — 키워드 선택

- **상세 설명**: 사용자가 6개 키워드 중 1개를 선택해 면접 방향을 지정한다.
- **처리 로직**: 키워드 목록 — 데이터전처리 / DB / 부하 / 보안 / 시스템설계 / 클라우드
- **출력/결과**: `keywords` 배열
- **관련 API**: `KW-001`, `IS-001`
- **기획서 근거**: 4장 공통규칙
- **오너**: 김한비

### FR-03 — 페르소나 질문 생성

- **상세 설명**: 추출 텍스트+선택 키워드 기반으로 실무형 질문 3개를 일괄 생성한다.
- **입력**: `extractedText`, `keyword`, `interviewerId`, `userName`
- **처리 로직**:
  1. 페르소나별 System Prompt 로드
  2. 이력서+키워드 프롬프트 동적 주입
  3. 참고 질문 예시(few-shot)를 프롬프트에 포함
  4. LLM(Claude) 호출 시 질문 3개 + 각 질문의 모범답변(예상답변)을 함께 생성 (7/9, API 호출 횟수 유지)
  5. 생성된 질문은 `Message`(role=QUESTION)로 먼저 저장하고, 그 모범답변은 `questions`
     테이블(`messageId` 단일 PK/FK → `Message.id`, `expectedAnswer`)에 저장한다 —
     `questionText`는 별도 저장하지 않는다(`Message.content`에 이미 있음). 질문생성
     LLM과 채점 LLM이 분리된 구조라, 여기서 저장해 둔 모범답변을 FR-04 채점 호출에서
     사용자 답변과 함께 재사용한다(생성 시점 정정 `open-questions.md` #9, 키 설계는
     2026-07-14 `messageId` 단일 PK/FK로 번복)
  6. 프론트에는 질문만 1개씩 순차 노출, 모범답변은 API·화면에 노출 안 함(채점 로직 내부
     전용 — MVP 채점 정확도 목적이며 스트레치골 FEAT-15 데이터 플라이휠과는 무관)
- **출력/결과**: 질문 3개 배열(`questionId` 1~3), `questions` 테이블에 모범답변 저장
- **예외처리**: LLM 응답 스키마 오류 시 최대 2회 재요청
- **관련 API**: `IS-001`
- **기획서 근거**: 3장#2, 7/9(few-shot)
- **오너**: 김한비

### FR-04 — 판정 방식 (배치채점 + 꼬리질문)

- **상세 설명**: 답변 3개를 일괄 채점하고, 최저 점수 답변 1개에 꼬리질문을 무조건 발동한다.
- **입력**: `answers[](questionId, answerText)` 3개
- **처리 로직**:
  1. 모범답변(예상답변)은 질문 생성 호출(FR-03)에서 이미 생성해 `questions` 테이블에
     저장되어 있음 — 채점 호출은 새로 생성하지 않고 현재 답변이 속한 질문
     `Message.id`(`messageId`)로 저장된 값을 조회해 사용자 답변과 비교한다(문구 정정:
     "채점 호출 내 생성" → "질문 생성 호출 내 생성", 최용성 확인 완료, `open-questions.md`
     #9. 조회 키는 2026-07-14 `{sessionId, questionId}`에서 `messageId`로 번복)
  2. 문항당 5개 세부항목 기준 채점: 기술적정확성10 / 핵심내용충족도5 / 근거판단과정4 / 구체성실무연계3 / 트레이드오프예외3 = 25점
  3. 각 항목은 6단계 세부 점수 구간표 기준으로 산정(별도 문서 "채점 기준 로직 설계" 참고)
  4. 세부항목 점수는 API·화면에 노출 안 함(내부용)
  5. 3개 중 최저점 1개 식별(동점 시 랜덤)
  6. 최저점 `questionId`를 질문 생성 LLM에 전달하고, 꼬리질문(`questionId=4`)과 해당
     비노출 예상답변을 생성해 `questions` 테이블에 저장(위 1번과 동일한 방식 — 질문
     생성 호출에서 저장, 채점 호출은 재사용)
  7. interview 계층이 최초 3문항의 질문·답변·예상답변과 꼬리질문 쌍을 합쳐
     questionId `{1,2,3,4}`를 최종 채점 LLM에 전달
  8. 4문항을 같은 5개 루브릭으로 재채점한 뒤 합산(100점 만점)하고 종합 피드백 생성
  - ⚠️ AI가 한 번에 20개 세부 숫자를 정확히 산정해야 해서 JSON 파싱 실패·숫자 누락 리스크 증가 — NFR-05(최대 2회 재요청, 스키마 검증, 점수 클램핑) 방어로직의 중요도가 더 높아짐
- **출력/결과**: 최초 응답은 `evaluations` 3개와 `weakestQuestionId`, 최종 응답은
  `evaluations` 4개와 `totalScore`(0~100), `passed`, `overallFeedback`을 반환한다.
- **예외처리**: 동점 처리(랜덤), LLM 응답 스키마 검증 실패 시 재요청
- **관련 API**: `IS-002`
- **기획서 근거**: 3장#3, 7/9(모범답변 비교 채점 방식, 세부 점수구간표 노션 백엔드 아이디어 채택)
- **오너**: 김한비(LLM 호출) → 최용성(루브릭 적용부터)

### FR-05 — 레벨 해금 및 진행도 게이지

- **상세 설명**: 판정 결과 80점 이상 시 다음 레벨을 해금하고, 계정 전체 진행도 게이지를 누적한다.
  게이지 증가폭은 균등하지 않다(✅ 2026-07-10 확정: Lv.1 클리어 +30% / Lv.2 클리어 +30% /
  Lv.3 클리어 +40% = 100%). `docs/requirements/open-questions.md` #3 참고.
- **입력**: `totalScore`(0~100)
- **처리 로직**:
  1. 80점 이상이면 `UserUnlockStatus.unlocked_level` 갱신
  2. 레벨 클리어마다 `progress_gauge` 증가 — Lv.1→+30 / Lv.2→+30 / Lv.3→+40. 하드코딩
     금지, 레벨별 증가폭을 상수/설정으로 분리한다(레벨 순서와 1:1 매핑, 균등 분배 아님).
  3. 80점 미만이면 Fail
- **출력/결과**: `unlockedLevel`, `progressGauge`
- **예외처리**: 미달 시 상태 변화 없음
- **관련 API**: `IS-002`, `IV-001`, `UM-001`
- **기획서 근거**: 3장#4
- **오너**: 최용성

### FR-06 — OAuth2(Google) 로그인

- **상세 설명**: Google OAuth2로 로그인하고 유저별 레벨/해금 상태를 저장한다.
- **입력**: Google OAuth2 인증 코드
- **처리 로직**:
  1. 커스텀 경로로 흐름 구성
  2. JWT Access Token 발급(30분)
  3. Refresh Token은 HttpOnly/Secure 쿠키로 별도 발급
- **출력/결과**: `accessToken`, `user` 정보
- **예외처리**: 인증 실패 401, Refresh Token 만료 시 재로그인 유도
- **관련 API**: `AU-001~004`
- **기획서 근거**: 3장#5, 17장
- **오너**: 표지민

- **처리 로직**: React+TS+Tailwind로 구현, 각 도메인 담당자가 자기 API 직접 연동

- **관련 API**: 전체 API
- **기획서 근거**: 3장#6
- **오너**: 표지민

### FR-08 — 종합 피드백

- **상세 설명**: 3개 답변 전체를 종합한 피드백 하나를 사용자에게 제공한다.
- **입력**: `totalScore`, `evaluations[]`
- **처리 로직**: 꼬리질문 재채점 시점에 3개 답변 전체 맥락을 참고해 종합 코멘트 생성
- **출력/결과**: `overallFeedback`(텍스트)
- **관련 API**: `IS-002`(2번째 호출)
- **기획서 근거**: 3장#7
- **오너**: 김한비

### FR-09 — 뱃지 지급

- **상세 설명**: 가입/레벨 해금 시점에 4단계 성장형 뱃지를 지급한다.
- **입력**: 트리거 이벤트(가입완료, Lv.1/Lv.2/Lv.3 해금)
- **처리 로직**:
  1. 가입 직후 → Stage1 지급
  2. Lv.1(널널한 대리) 해금 → Stage2 지급
  3. Lv.2(깐깐한 과장) 해금 → Stage3 지급
  4. Stage4는 Lv.3(압박 페르소나, 스트레치골) 해금 시에만 지급 — **MVP 범위에서는 실제 지급 불가**, Lv.3 구현 시(스트레치골 달성 시)에만 활성화
  5. `UserBadge` 레코드 생성
- **출력/결과**: `UserBadge` 레코드
- **관련 API**: `BG-001`
- **기획서 근거**: 5장 뱃지 시스템
- **오너**: 최용성(트리거 판정) / 표지민·이건희(가입·업로드 이벤트 발행)

### FR-10 — 채팅 히스토리 사이드바

- **상세 설명**: 레벨별 폴더 구조로 과거 면접 세션·채팅 로그를 조회한다.
- **처리 로직**: 기존 `InterviewSession`+`Message` 데이터를 level 기준으로 그룹핑해 반환
- **출력/결과**: 레벨별 세션 목록, 세션별 메시지 로그
- **예외처리**: ⚠️ MVP 필수 아님 — ERD엔 대비해두었으나 실제 API 구현은 일정 보고 결정(스트레치골 성격 유지)
- **관련 API**: `HS-001`
- **기획서 근거**: 5-1장 스트레치골 → 정식 반영
- **오너**: 최용성

### FR-11 — 이력서 PII 마스킹

- **상세 설명**: 추출된 이력서 텍스트에서 이메일 등 민감정보를 식별해 마스킹 처리한다.
- **입력**: `extractedText`(원본)
- **처리 로직**:
  1. 정규식/패턴으로 이메일 탐지
  2. 마스킹 처리 후 DB 저장(원본 미저장)
- **출력/결과**: `extractedText`(마스킹됨)
- **기획서 근거**: 14장 개인정보처리방침 연계 (개발 후 고려)
- **관련 API**: `RS-001`
- **오너**: 이건희

### FR-12 — 개인화 (이름 반영)

- **상세 설명**: 마이페이지에서 이름을 수정할 수 있고, 면접 질문/피드백에 사용자 이름을 반영한다.
- **입력**: `name`(수정할 이름)
- **처리 로직**:
  1. PATCH로 `users.name` 갱신
  2. 이후 질문 생성/피드백 생성 프롬프트에 사용자 이름 동적 주입(예: "OO님, ...")
- **출력/결과**: 수정된 `name`, 이름 반영된 질문/피드백 텍스트
- **관련 API**: `UP-001`, `IS-001`, `IS-002`
- **기획서 근거**: 3장#8, 7/9 신규
- **오너**: 표지민(PATCH API) / 김한비(프롬프트 주입)

### FR-13 — 레벨별 등급 참고 텍스트 표기

- **상세 설명**: 레벨 옆에 "[분야] 기초/중급/심화 수준" 등 주니어·미들·시니어 참고용 설명을 병기한다.
- **입력**: `level`(1~3)
- **처리 로직**: 프론트에서 level 숫자에 정적 텍스트를 하드코딩 매핑해 표시 (백엔드 로직·필드 변경 없음, 확정)
- **출력/결과**: 화면 표시 텍스트 (백엔드 응답 아님)
- **관련 API**: `IV-001`
- **기획서 근거**: 3장#4, 7/9 확정 — 이전 `ScoreTierConfig` 설계 정정
- **오너**: 표지민(프론트)
