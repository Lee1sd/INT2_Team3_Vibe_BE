# test-strategy.md — 테스트 전략

> 원본: `[기획서] 커리어 던전 v5.1.pdf` 18장. 이 문서는 `docs/ai/SHARED.md` §3 역방향
> 추적 ④(테스트 파일)의 판단 기준입니다 — "테스트가 있는가?"뿐 아니라 "어떤 시점에
> 어떤 종류의 테스트가 있어야 하는가"까지 다룹니다.

## 1. 단위 테스트

- 시점: 개발 중 / 대상: Service 레이어 중심 / 목표: 핵심 비즈니스 로직 **70% 커버리지**
- 도메인별 중점 대상:
  - ① 파일 파이프라인: 파일 검증 로직, try-finally 삭제 보장
  - ② 면접 엔진: 프롬프트 조립 로직, JSON 파싱 방어(재시도), attempt 상태 분기
  - ③ 평가·게이지·해금: 루브릭 채점 로직, 게이지 환산 규칙, 해금 판정 조건
  - ④ 인증: JWT 발급·검증·만료 처리, Refresh Token 로테이션

텍스트 캐싱(사용자ID+파일해시 기반 재파싱 방지)은 이번 프로젝트 스코프에서 제외하므로
캐싱 키 생성 테스트도 이번 테스트 범위에서 제외합니다. 파일 크기 제한(최대 10MB)과 예상
사용자 규모를 고려했을 때, 캐싱으로 얻는 성능 이점보다 캐시 관리(무효화, TTL, 동시성 등)
복잡도가 더 크다고 판단했습니다. 향후 확장을 위한 `fileHash`, `cacheExpiresAt`, `EXPIRED`
설계와 30일 개인정보 파기 배치 테스트는 유지합니다.

## 2. 통합 테스트

- 시점: 3주차 통합 전 / 대상: E2E 흐름 / 목표: 도메인 간 연결 검증
- 필수 시나리오:
  - 업로드: 업로드 → 텍스트 추출 → 캐싱 확인
  - 면접: 세션 시작 → 질문 생성 → 답변 제출 → 채점 → 게이지 반영
  - 해금: 해금 조건 도달 → 다음 페르소나 해금 확인
  - 인증: Refresh Token 만료 → 재발급 → 정상 응답 확인

## 3. LLM 응답 품질 테스트

- 시점: **2주차 LLM 실연동 직후** (`docs/requirements/milestones.md` 2주차 마일스톤과
  연동) / 대상: 샘플 이력서 / 목표: 일관성 및 파싱 안정성 검증
- 확인 항목: 질문이 이력서 내용과 관련 있는지 / 페르소나 톤이 일관되는지 / JSON 파싱
  실패가 없는지

## 4. Mock 활용 전략

- 시점: 개발 전체 기간 / 대상: LLM 모드 / 목표: 비용 차단 및 안정성
- 개발 중에는 Mock LLM 모드(고정 JSON 반환)를 사용한다.
- 실 API 호출은 통합 테스트와 데모 리허설에만 한정한다.
- 공용 API 키는 월 예산 상한(hard limit) 설정이 필수다.
- (상세 정책은 `docs/operations/llm-cost-policy.md`가 SSOT — 이 절은 요약만 유지)

## 5. 완료 조건과의 연결

`.github/PULL_REQUEST_TEMPLATE.md`의 "테스트" 체크리스트(로컬 동작 확인, 빌드/테스트
통과, 성공/실패 케이스 확인, 검증/예외 처리 확인)는 이 전략의 "단위 테스트" 절을
최소 기준으로 삼습니다. 통합/LLM 품질 테스트까지 필요한 PR인지는 리뷰어가 판단합니다.
